§ 1

Summary and rationale

The Lingua Franca Run-Time Infrastructure (RTI) coordinates a federation by deciding, for each scheduling node, whether it may safely advance to a requested tag — that is, whether no input with an earlier or equal tag can still arrive. That decision is a monotone computation over a small, fixed-shape state table and a cached all-pairs minimum-delay matrix. In software it is serialized behind one coarse mutex and re-evaluated per transitive downstream node on every Next Event Tag message (NET), giving a fan-out cost of O(n·(n·d)) per message. In hardware the same computation is a pipelined reduction that can be evaluated for all nodes concurrently.

How to read Figure 1. Its upstreams can still send, but no input reaches e earlier than the sender’s NET plus the connection delay; the least of these is the earliest incoming message tag, EIMT = 17 ms. Every tag at or below g lies where no input can arrive, so e is granted — and granted maximally, up to the latest tag below EIMT. Had u1 reported NET = 10 ms, EIMT would equal g and e would have to wait.

HW-RTI is a synthesizable implementation of that decision engine. It targets the case where the coordinator, not the transport, dominates coordination latency: federations whose members are reactor-chisel modules and/or CPU cores on a single SoC, communicating over AXI or a network-on-chip rather than TCP.

1.1 Why this is worth building

It closes a real gap in reactor-chisel. The existing hardware runtime's TriggerGenerator already emits NET and Logical Tag Complete (LTC) messages and consumes a Tag Advance Grant (TAG) — but for standalone FPGA designs that TAG input is hardwired to a forever tag, meaning the design self-grants and no coordination occurs. HW-RTI is precisely the module that replaces that constant, through the port adapter of §8.1, turning a multi-reactor FPGA design into a genuine federation with enforced timestamp order.

The bottleneck inverts. The software RTI's dominant cost is notification fan-out, which is sequential only because a CPU has one thread of control. Instantiating per-node decision units removes the serialization: every message costs the same fixed time whether it reaches one node or all of them, converting the classic “broker becomes a bottleneck” criticism into a non-issue at on-chip scale. That fixed time still grows with the size of the federation the core is built for (§1.3); what disappears is its dependence on each message’s reach.

Latency becomes statically bounded. A software RTI's response time is a distribution with a long tail; HW-RTI's is a closed-form function of elaboration-time parameters. This is the claim that distinguishes the project from “make it faster,” and §1.3 develops it in full.

1.2 Why the algorithm suits fabric

Three structural properties, each load-bearing for the design that follows:

Bounded, pointer-free state. A scheduling node is five tags plus flags and small index arrays — no allocation, no chasing, on the decision path.

Path-delay composition is associative. Each connection delay is a function on tags, and path composition is function composition, hence associative — though not commutative, as the reference implementation warns. Delays are also monotone (a ≤ b implies a⊕d ≤ b⊕d), which provides the distributivity that closure algorithms require. The minimum-delay matrix is therefore a transitive closure over an ordered monoid — structurally a tropical (min-plus) closure, for which systolic arrays are a mature FPGA idiom.

The hot operation is a reduction. The Earliest Incoming Message Tag (EIMT) — the earliest tag at which anything could still arrive — is a minimum over transitive upstreams of (NET ⊕ path delay): n tag-adders feeding a comparator tree of depth ⌈log₂n⌉.

Scope limit. Hardening the coordinator only pays when the transport is faster than the decision. Over Ethernet with a kernel network stack, per-message overhead is on the order of 10–50 µs (a planning estimate, to be replaced by the measurements of §11), and a decision of about 150 ns (a design target derived from the cycle counts of §1.3, not a synthesis result) would save a few percent. Phase 1 therefore excludes TCP entirely and targets on-chip federations, where the decision genuinely is the critical path. See §2.2.

1.3 Latency as a derived quantity

“Statically bounded” is a stronger claim than “fast,” and stronger than the usual worst-case bound. For a fixed elaboration configuration and under assumptions A-1–A-3 below, HW-RTI's target is a constant evaluation latency K after message acceptance: a number computed from parameters fixed at elaboration, identical for every accepted message, and derivable without running the design. Grant and response latencies have the separately stated bounds below (grant latency in [K, Kmax]; response latency adds queueing) and may vary within them. A WCET analysis produces an upper bound that is typically pessimistic and always requires justification; a fixed-latency pipeline produces a number that is itself the answer.

The closed form

Every stage of §9.1 is either a constant or logarithmic in a structural parameter, plus one term set by the area parameter P_EIMT. Writing n for the node count and d for the maximum in-degree, the evaluation latency — from accepting a message to having every node’s grant decided and ready to leave — is:

K = 10 + ⌈log₂n⌉ + 2·⌈log₂d⌉ + ⌈n/P_EIMT⌉ − 1 cycles

— the constant 10 covering decode, state write, and dispatch; the ⌈log₂n⌉ term the EIMT reduction tree; the two ⌈log₂d⌉ terms the tightening pass and the Phase 1 minimum over immediate upstreams; and the last term the extra rounds when fewer than n trees are built (§5.2). Three quantities, not one. K is what is fixed, and only K. Two other quantities are bounded rather than constant, and any latency claim must state which one it refers to. The grant latency, from acceptance to the last grant a message produces, equals K when no PTAG walk runs. A walk adds at most n − 1 cycles per distinct PTAG tag in the evaluation, and there are at most z of them, z being the number of nodes flagged as members of a zero-delay cycle (§7.6, one iteration per cycle); and the merge then emits a single grant per node (D-9), so no channel carries more than one grant per message. Hence K ≤ Lgrant ≤ Kmax = K + (n − 1)·z, with Kmax = K in any federation without zero-delay cycles. DNETs inform rather than grant and leave within about n + 5 cycles when the full recomputation runs (§5.2, from the stage costs of §9.1). Messages that produce no grant — a MSG_SENT that does not lower a next event, or a NET whose cascade changes no node’s answer — have no grant latency at all; for them the measure is K. The third quantity is the interval I at which the sequencer accepts messages, which sets throughput and queueing (§7.2).

The design rules that make it true

A fixed latency is not automatic in hardware; it is obtained by forgoing several optimizations that would otherwise be natural. These are binding constraints on the implementation, not observations about it:

The one variable term, and the assumptions

Honesty requires naming what is not constant. If several federates present messages in the same cycle, arbitration queues them; a message can wait behind at most n−1 others, each occupying the sequencer for the throughput interval of NFR-02. The complete statement is therefore:

Lresponse ≤ (n−1)·I + Kmax

— bounded, structural, and still small (at n = 16, d = 4, P_EIMT = n, no zero-delay cycles and DNET enabled, I = 17 and the bound is 273 cycles ≈ 1.37 µs at 200 MHz), but a bound rather than a constant. What is constant is K, per message once accepted. Three further preconditions must be stated with the property, since each is a way the bound leaks:

Why a constant is worth more than a small mean

It removes the coordinator from WCET analysis as an unknown. In centralized coordination every tag advance is blocked on a round trip, so coordination latency enters the application's end-to-end timing directly. Analyzed against a distribution, that term must be a measured maximum plus defensive margin. Analyzed against K and Kmax, it is exact. Put in the vocabulary of the PRET literature: a software coordinator reintroduces a system-level state problem even when every federate runs on a machine built to eliminate it. HW-RTI keeps the analysis a path problem end to end — which is what would let an InterPRET-class system make timing claims about centralized coordination, which the reference software RTI examined in this document (lf-lang/reactor-c on GitHub, commit ccd0512) does not support; no wider survey of implementations is claimed.

It lets physical-time budgets be sized rather than guessed. Deadlines and — where federations mix modes — safe-to-process offsets must absorb coordination delay. Absorbing 50 µs of jitter consumes a significant part of the timing budget; a fixed coordination term of about 90 ns, derived from the cycle count of §1.3 at 200 MHz and a design target until M-2 reports synthesis and timing, is far smaller and can be budgeted explicitly. The knock-on effect is tighter after delays and lower end-to-end latency for the same safety argument, which is what KPI-4 measures.

It makes timing reproducible, not merely deterministic. Given identical tagged inputs and deterministic reaction bodies, Lingua Franca already guarantees that values and logical order repeat; physical timing never did. A coordinator with constant evaluation latency, over deterministic federates and under identical cycle-stamped input and reset traces (NFR-07), is intended to yield runs that repeat cycle for cycle. A timing anomaly then becomes a reproducible bug rather than a statistical observation — a qualitatively different debugging and certification process, and the kind of evidence (“derived from structure” rather than “observed over 10⁶ runs”) that safety arguments prefer.

How the claim is to be discharged. Structurally by rules L-1..L-6; empirically by PT-1, which asserts an identical evaluation cycle count across randomized tag values and topologies of equal shape; and formally by FV-6, which will check, by bounded model checking for n ≤ 4 and the depth stated in §10.3, that evaluation completes exactly K cycles after acceptance and that every grant leaves within Kmax. A claim covering all reachable states, or configurations larger than those checked, requires an additional inductive or completeness argument, for which rules L-1..L-6 are the intended basis; the result actually obtained will be reported separately from this statement of the property. A latency claim defended only by measurement would be exactly the weak form of evidence this subsection argues against.

The core is organized as a shared state table surrounded by fixed-function engines, driven by a small sequencer. The design principle throughout: keep every engine value-independent in timing, so latency is a function of topology size only (NFR-01).

5.2 Matrix organization and the read pattern

D-2 specifies where the matrix is stored; the access pattern determines how it must be organized, and that is the harder constraint. Every message re-evaluates all n nodes (L-2), and the plain-EIMT pass of §7.4 reads column e for every e — the whole matrix, n² entries of 96 bits, on every accepted message. A single memory with two ports delivers at most two entries per cycle, so a monolithic BRAM would make that pass n²/2 cycles long (128 at n = 16), not the handful that §9.1 budgets. The matrix must therefore be banked by row: bank i holds row i, addressed by destination, and a read at address e returns minDelays[i][e] from all n banks in the same cycle — one full column per cycle per read port.

Row banks are shallow (depth n) and wide (96 bits), which is the shape distributed RAM serves and block RAM does not: a 36 Kb BRAM is 512 entries deep, so one bank per BRAM would leave over 90% of every block unused. In 7-series distributed RAM, which stores 32 × 6 bits in four LUTs, a bank of up to 32 entries costs 64 LUTs, so n banks cost about 0.5k LUT at n = 8, 1k at 16 and 2k at 32, per read port. NFR-08 leaves the choice of memory to synthesis; this records which way it should go and why. Two n×n bit matrices are stored beside it in flip-flops, both written when the closure is: A, the immediate adjacency, and R, reachability (R[i][j] iff minDelays[i][j] ≠ FOREVER). They answer every “is u upstream of e” question with one bit, without touching the tag matrix.

How many columns per cycle. The number of read ports is the parameter P_EIMT of §7.4: each port feeds one reduction tree, and the n nodes are processed in ⌈n/P_EIMT⌉ rounds. Its two limits pull against G-2 and G-5, and this document has so far quoted each at a different setting. The closed form of §1.3 and the 6-cycle entry of §9.1 assume P_EIMT = n; the EIMT row of §9.3 is a single tree (n × (tagAdd + comparator) ≈ 16 × 170 ≈ 2.7k LUT at n = 16). 5.3 From a sequential cascade to one parallel evaluation

The reference handles a message as a cascade of function calls executed one after another under the global lock; HW-RTI handles it as one evaluation of every node against a single snapshot of the state table. The two agree on what is decided, but not automatically on what is emitted, because some writes made early in the cascade are read later in it. Why emission is masked. For a node outside the reference's set, evaluating anyway is almost always silent: none of its decision inputs involves the sender, so it reaches the answer it reached last time and its redundancy guards suppress it. “Almost” matters for G-1. A node's inputs can also change without a message — the control plane writes MAX_STOP_TAG, or a node becomes NOT_CONNECTED — and a node whose decision changed that way would be granted by an unmasked core at the next message of any kind, but by the reference only when a message whose cascade reaches it arrives. The mask is one row of R and an AND per node. It leaves the timing of L-2 intact, because every unit still evaluates.

Three effects of execution order. Within one cascade the reference writes state that later steps read. The core evaluates against a snapshot, so each write needs an explicit rule.

  1. The start-tag write-back. When EIMT, the tightening pass or strict EIMT reads an upstream whose next_event is still NEVER, the reference does not merely substitute the start tag: it stores it. From then on that node looks, to every later reader, as if it had reported NET = start tag — including its own decision, whose trichotomy requires NET > NEVER. Which nodes receive the write-back, and whether a node is evaluated before or after its own write-back in the same cascade, depends on index order. The core applies the write-back at the end of the evaluation, to every connected node read by a decision that reached the EIMT stage. The two can differ only while some node has never sent a NET, so the DT-1 harness opens every trace with one NET per node, and the startup window is recorded as a divergence (DL-7).
  2. Grants seen by later decisions. Each emitted TAG or PTAG updates last_granted or last_provisionally_granted at once, and every later decision in the cascade — including those of the PTAG walk (§7.6) — tests its guards against the new values. In the core, one node can therefore hold candidates from two sources in one evaluation: its own decision unit and the propagator. The dispatcher merges them per node (D-9) by the authorization order: TAG(y) authorizes every tag up to y, PTAG(g) every tag strictly before g plus a provisional g, so TAG(y) is weaker than PTAG(g) exactly when y < g, and PTAG(g) is weaker than TAG(y) when g ≤ y. The merge emits only the strongest candidate, and at an equal-tag TAG/PTAG tie it keeps the PTAG. The reference, applying the same candidates one at a time, emits the strongest in every order — it always passes the guards — and some of the weaker ones in some orders: with TAG(5) and PTAG(10), ascending order sends both, descending only PTAG(10). The weaker grants carry nothing the strongest does not, so they are dropped from the comparison on both sides (the contract below), and the per-node state then agrees in every order, because every guard reads the pair (last_granted, last_provisionally_granted) only through its larger member and which of the two it is. The one order dependence left is the equal-tag tie: a TAG from the walk and a PTAG from the node’s own decision, which the reference resolves either way and the core resolves toward the weaker grant. It needs the walk’s plain EIMT to exceed the decision’s tightened one. With every node connected the two coincide, since each tightening term is a path the matrix already minimizes over (associativity and monotonicity, FV-2), so in Phase 1 the tie can arise only after a RESIGN at the end of a run. It is still worth raising upstream: the tightening pass exists, by the source’s own comment, to prevent over-granting, and the walk skips it.
  3. Emission order across nodes. The reference emits in the order it evaluates; the core emits one evaluation's grants in parallel on per-node channels (§7.8). A node can observe another node's grant only through a later message, so order across nodes carries no information. The DT-1 comparator treats the grants produced by one input message as a set.

The equivalence contract. Together these rules define what G-1 promises, and it is narrower than bit-for-bit equality of message streams. Compared, for each input message and each node: the strongest grant under the authorization order, the DNET value, and the pair (lastGranted, lastPtag) read through its larger member. Abstracted, on both sides: the order of grants to different nodes, any grant weaker than another grant to the same node in the same message, and a lastPtag at or below lastGranted. Excluded, and recorded as divergences (DL-7): (i) the startup window, where the start-tag write-back depends on evaluation order — the harness runs it as a preamble of one NET per node whose grants are not compared; once every node has sent a NET no next event is NEVER, the write-back cannot recur, and the two models are compared from the first message after the preamble, provided their normalized per-node states agree at its end (a disagreement is counted here); (ii) an equal-tag tie between a TAG from the PTAG walk and a PTAG from the node’s own decision, where the core keeps the PTAG; and (iii) an insertion into a full in-transit set, an error in the core that cannot occur in the reference. Configurations outside the fidelity boundary of §10.2 — transient federates above all — are out of scope rather than excluded. The harness must detect each excluded case and report its count: a trace that enters one is set aside, never counted as a pass.

Why minInTransit is a field and not a wire. 7.1 Transport adapter

Purpose. Normalize every inbound source into a single decoded control message stream, and fan decoded outbound messages back to the right federate.

Interface. Per hardware federate, a ready/valid pair of channels (Decoupled(ControlMsg) inbound, Decoupled(Grant) outbound). For software federates, an AXI4-Lite shim with a per-federate mailbox (§8.2). A round-robin arbiter selects one inbound message per cycle; arbitration is the only source of nondeterminism in the core, so it must be fair and, for reproducibility, a deterministic function of a rotating priority register (NFR-07).

Why the data plane must not race the LTC (FR-19). Safety against a message the coordinator has not yet seen rests on NET, not on the data path: while u reports NET = g, EIMT(w) is bounded by g plus the connection delay, so no grant can pass it. MSG_SENT is likewise harmless — it only lowers w's next event, never authorizes an advance. The single dangerous message is LTC, because it unlocks the Phase 1 fast path: if u's LTC(g) reaches the coordinator before u's own data reaches w on the separate on-chip channel, w can be granted past g while that input is still in flight. Hence FR-19 and assumption A-4: the federate binding must make the write visible before asserting LTC.

How to read Figure 8. Left: the LTC arrives first, the fast path grants w past g, and u’s message then lands in w’s past. Right: the federate binding waits until the write is visible before asserting LTC (FR-19, A-4), so every grant follows the data it depends on.

MSG_SENT notification. When federate u sends application data to w at tag g, the sending logic pulses a notification to HW-RTI. This matters because the reference RTI learns about progress from routing messages; since HW-RTI does not route (NG-6), the notification restores that information so nextEvent(w) can be lowered as the reference does. The rule must be stated carefully, because the reference does not lower a stored value once — it re-applies the bound on every NET it receives from w, and releases it only when w’s LTC passes the tag in question. The hardware equivalent is nextEvent(w) := min(NET(w), minInTransit(w)) evaluated at each NET, with minInTransit written by MSG_SENT and cleared by LTC (§6.3). A design that merely lowers nextEvent(w) when the notification arrives loses the bound at w’s next NET, which is exactly when the federate is most likely to report a tag beyond the message still crossing to it.

What the notification carries, and when the core acts on it. The reference records, for destination w, the tag carried in the forwarded message's header (intended_tag); the delay-adjusted arrival_tag it also computes is used only for transient admission. It records the tag only if w has not yet completed it, and each distinct tag once. It then treats the message as a NET from w whenever the tag is below w's recorded next event, running the whole NET cascade of §5.3. A MSG_SENT above w's next event changes the in-transit set and nothing else.

The in-transit set in hardware (D-10). The reference's per-federate priority queue is used for three operations only: insert if absent, remove every tag at or below a completed tag, and read the minimum. Over a fixed array of Q entries per node these are a parallel equality compare, a parallel ≤ compare and a Q-input minimum tree. Each message touches one destination's set, so one bank of Q comparators and one tree serve all n nodes: the entries are stored in distributed RAM, n deep and Q × 96 bits wide, and only the selected node's row is read, updated and written back. The minimum goes into the node's minInTransit field (§6.3), which is what the NET path reads, so the field and its role are unchanged, and Q = 1 is exactly the single-register design. The NET path of a MSG_SENT needs min(old, g), which the register already provides; the removal after an LTC is read by no decision of that cascade and completes in EMIT.

When the set is full. Q is fixed at elaboration, and the number of distinct tags in flight to one node is not bounded by the topology alone. Dropping an entry is unsafe: the bound it provides would vanish while its message is still in flight. Merging entries into a (low, high) range is safe — after an LTC between the two, low may rise only to the successor of the completed tag — but it makes the clamp pessimistic. In a cycle, a pessimistic clamp on a node's own next event caps its own EIMT, and in a zero-delay cycle that can reduce progress to one microstep per round trip. Phase 1 therefore treats overflow as an error (FR-18) and sizes Q from the system-test corpus; the merge stays an option under OQ-4.

7.2 Sequencer

A four-state finite-state machine, with states named for what they do: IDLE (awaiting a message) → UPDATE (write it to the state table) → DECIDE (evaluate grants) → EMIT (send them). UPDATE writes the accepted message into the state table; DECIDE asserts evaluate to the decision array and waits the fixed pipeline depth; EMIT drains the dispatcher's grant queue. A CLOSURE super-state pre-empts all of these when the control plane signals a topology change (FR-16), blocking decisions until the matrix is valid.

Because the evaluation latency is fixed (NFR-01), the FSM uses a counter rather than handshakes with the engines — simpler, and it makes the latency property structurally obvious to a reviewer.

Overlap, and the interval it allows. The loop is not a pipeline, and the throughput it can sustain follows from what may overlap. Arbitration and decoding of the next message (2 cycles) can proceed while the current one is still being evaluated, and dispatching the current grants (2 cycles) can proceed while the next message is written to the state table, because the merge (§5.3) has already written every grant’s effect into lastGranted and lastPtag before dispatch begins. Nothing else overlaps: the next UPDATE must wait for the current merge and, with DNET enabled, for the DNET engine to finish streaming the columns it reads (§5.2). Hence I = Kmax − 4, or max(Kmax − 4, n + 1) with DNET enabled. To keep I independent of data (L-1), the counter always reserves the worst-case walk time, whether or not a walk runs. At n = 16, d = 4, P_EIMT = n and z = 0 this is 14 cycles, or 17 with DNET — not the 8 an earlier draft assumed, which this sequencer never supported. Going lower means overlapping evaluations, which requires forwarding one merge’s writes into the next evaluation; that is Phase 2 material.

The steps of Figure 9

  1. IDLE. The sequencer waits for the arbiter to hand it a message; transition 1 is the message being accepted.
  2. UPDATE. The accepted message is written into the state table, in one cycle; transition 2 leaves as soon as the write is registered.
  3. DECIDE. The sequencer asserts evaluate to the decision array and waits the fixed pipeline depth, counted by a counter rather than by a handshake with the engines; transition 3 fires when the counter reaches that depth.
  4. EMIT. The dispatcher’s grant queue is drained to the per-node channels, and transition 4 returns to IDLE. A MSG_SENT that lowers no next event emits nothing here but still occupies the full interval, so throughput does not depend on the data.
  5. CLOSURE. A topology change signalled by the control plane (FR-16) pre-empts the whole loop while the matrix is rebuilt, in O(n³/P) cycles; the loop resumes only when the closure is valid.

How to read Figure 9. Because of the counter, the time from accepting a message to completing its evaluation is the same constant, K, for every message, and emission and the next acceptance follow at bounded offsets fixed at build time (NFR-01, NFR-02, FV-6). CLOSURE pre-empts the whole loop while the matrix is rebuilt and returns only when it is valid. A MSG_SENT that does not lower a next event emits nothing but still occupies the full interval. During Play a dot follows the current state.

7.3 Closure engine

Purpose. Compute minDelays[i][j] = least composed delay over all paths i→j, plus the two cycle flags (FR-05).

Algorithm. Blocked Floyd–Warshall over the ordered monoid of §6.2:

for k in 0 until n:                       // pivot
  for i in 0 until n:  (parallel over PEs)
    for j in 0 until n:                   // pipelined
      cand = minDelays[i][k] ⊕ minDelays[k][j]     // order: i→k then k→j
      if cand < minDelays[i][j]: minDelays[i][j] = cand
// cycle flags
inCycle[i] = (minDelays[i][i] != FOREVER)
inZdc[i]   = inCycle[i] && (minDelays[i][i] == ZERO_TAG)

Implementation. A linear array of P processing elements, each a tagAdd plus a cmp/mux, streaming rows from BRAM. Runtime is O(n³/P) cycles; at n = 32, P = 8 that is ~4k cycles (≈20 µs at 200 MHz) — irrelevant, since it runs once at startup in Phase 1.

Deviation from the reference, and why it is safe. The C implementation uses a sparse per-node relaxation, not Floyd–Warshall, and detects cycles as a side effect of the relaxation returning to its start node. Both compute the same mathematical object; equivalence is not obvious by inspection and is therefore an explicit verification obligation (DT-2), checked by comparing whole matrices and flag vectors over randomized topologies including multi-cycle and disconnected graphs.

7.4 EIMT engine

Purpose. For a target node e, compute EIMT and strict EIMT (FR-06).

// EIMT: over the matrix COLUMN for e
leaves[i] = if (minDelays[i][e] == FOREVER) FOREVER
            else tagAdd(netOrStart(i), minDelays[i][e])
EIMT(e)   = minReduce(leaves)                       // depth ⌈log₂n⌉

// Tightening pass (FR-06, mirrors the reference's second loop):
for u in immediateUpstreams(e):
  EIMT(e) = min(EIMT(e), delay(min(nextEvent(u), EIMT(u)), edgeDelay(u,e)))

// Strict EIMT: immediate upstreams only, skipping ZDC members
EIMT_strict(e) = min over u ∈ immUp(e), !inZdc(u) of
                   delay(min(nextEvent(u), EIMT(u)), edgeDelay(u,e))

Note the recursion. Both the tightening pass and strict EIMT reference EIMT(u) for immediate upstreams. Hardware cannot recurse, so the engine computes the plain EIMT for all n nodes first (n parallel reduction trees, or one tree time-multiplexed over n cycles), registers the vector, and only then evaluates the tightening and strict passes against that registered vector. This two-pass structure is the key scheduling decision in the whole core; it costs one extra pipeline stage and removes all recursion.

Cost. One tree is n tagAdds + (n−1) cmp/mux, depth ⌈log₂n⌉ comparator levels, pipelined to one result per cycle. Building n trees is O(n²) hardware — affordable to n = 16, so for n = 32 the default build time-multiplexes a smaller bank of trees (parameter P_EIMT); §5.2 gives the memory organization this requires and the cost of each setting.

Disconnected nodes. A NOT_CONNECTED upstream contributes FOREVER to the plain pass and is skipped by the tightening pass. The strict pass, following the reference, skips zero-delay-cycle members but not disconnected nodes. In Phase 1 a node becomes disconnected only by RESIGN at the end of a run (FR-14), but the asymmetry is the reference's and is copied rather than tidied.

7.5 Decision unit

One instance per node (D-3). Pure combinational logic over registered inputs, in the three phases of the reference function:

Two guards in series. The figure shows the guards the decision function applies to its own inputs. The reference then passes each result through the notification layer, which applies a second pair to the value actually emitted: a TAG or PTAG is dropped unless its tag exceeds both lastGranted and lastPtag, and nothing is emitted to a node that is NOT_CONNECTED. The two layers are not redundant. The decision accepts a TAG when EIMT ≥ lastPtag — the equality is deliberate, and the source says it lets a TAG override an earlier PTAG — but the value emitted is latestEarlier(EIMT), which lies below EIMT, so at equality the notification layer drops it. The fast path and the FOREVER branch pass through the same pair. The decision unit's output therefore goes through an emission guard before the dispatcher's merge (§5.3); without it the core would emit grants the reference never sends.

7.6 PTAG propagator

Purpose. FR-10 — release an entire zero-delay cycle at once.

The reference walks upstream recursively, but — contrary to a natural reading of the code — it keeps no visited set while doing so. The heap-allocated visited array in rti_common.c belongs to a different walk: the downstream notification that follows an LTC. Upstream PTAG propagation is implemented in rti_remote.c and terminates only on its redundancy guards — a node already granted that tag or later returns immediately, so a cycle stops re-entering itself because the second visit conveys no new information. That is a termination argument about tag monotonicity, not about graph traversal, and it is the weaker of the two: it depends on the guards being exactly right, and it offers no bound on the number of visits, only the promise that they stop.

What each step of the walk does is readily misread, and the hardware must copy it exactly. From a node p that has just been sent PTAG(g), the reference visits every connected immediate upstream u of p — not only those on zero-delay connections — and decides for u with the same g, using u's plain EIMT (the untightened quantity of §7.4) and u's strict EIMT: TAG(g) if EIMT(u) > g; PTAG(g) if EIMT(u) = g and strict EIMT(u) > g; nothing otherwise. The TAG carries g itself, not latestEarlier(g). Only a node that receives a PTAG continues the walk, because propagation is implemented in the PTAG emission routine; a TAG ends it there. Both emissions pass the notification guards of §7.5.

The hardware version is therefore not a translation but a strengthening. A bounded fixed point over bit vectors carries an explicit frontier and an explicit visited set, so termination is structural rather than value-dependent:

frontier := onehot(p);  visited := onehot(p)            // p was sent PTAG(g)
repeat at most n−1 times:                            // a simple path visits each node once
  reach := (OR over f in frontier of A[·][f]) & connected & ~visited   // all immediate upstreams
  next  := 0
  for u in 0 until n where reach(u):                   // fully parallel
    if g > lastGranted(u) && g > lastPtag(u):          // notification guards
      if EIMT(u) > g:                              candidate(u, TAG,  g)
      else if EIMT(u) == g && EIMTstrict(u) > g:  candidate(u, PTAG, g); next(u) := 1
  visited := visited | reach;  frontier := next
until frontier == 0

Marking every reached node visited, not only those that continue, matches the reference: a second visit with the same g meets either a guard closed by the first visit's grant or the same inputs that produced nothing. Termination is structural (at most n − 1 iterations) and does not rely on the redundancy guards — they remain, but only to suppress redundant emissions. A is the immediate-adjacency bit matrix of §5.2, so each step is a bit-vector OR and one parallel test. Candidates go to the dispatcher's merge (§5.3), not straight to the channels, because the same node may also hold a candidate from its own decision unit.

More than one source. One evaluation can PTAG several nodes — the members of one zero-delay cycle with equal NETs, or members of different cycles. Sources with the same g share one walk: the frontier starts with all of them. Sources with distinct tags need separate walks, run in ascending tag order; the merge makes the result independent of that order. There are at most z distinct tags, where z is the number of nodes flagged inZdc, so the worst-case addition to K is (n − 1)·z cycles. That is still a constant of the topology, known once the closure is valid, but a federation with several independent zero-delay cycles can see it dominate K. Parallel walk lanes are the corresponding area/latency parameter.

7.7 DNET engine

Purpose. FR-11 — suppress NETs at or below each node’s DNET threshold.

for u where minDelays[u][e] != FOREVER, u != e:        // column e: upstreams of the sender
  if inZdc(u) || inZdc(e):  dnet = NEVER
  else:
    c = dnetSub(nextEvent(e), minDelays[u][e])            // the sender's own candidate
    if lastDnet(u) ≥ c:    dnet = c                       // the reference's shortcut
    else:  dnet = min over w ≠ u, minDelays[u][w] != FOREVER,
                  of dnetSub(nextEvent(w), minDelays[u][w])   // row u: the n-cycle stream of §5.2
  if dnet.time < startTime:  dnet = NEVER
  if connected(u) && dnet != lastDnet(u) && nextEvent(u) ≤ dnet:
    emit DNET(u, dnet);  lastDnet(u) := dnet

Three details are the reference's and must be copied, not improved. The fast path returns the sender's candidate whenever it does not exceed lastDnet(u), without looking at u's other downstreams. Recomputing the full minimum every time would be cleaner, and can differ whenever another downstream's next event has fallen since lastDnet(u) was written, which happens because a DNET that fails the emission test leaves lastDnet(u) unchanged. A result earlier than the start time becomes NEVER. And a zero-delay-cycle member, or any upstream of a sender in one, is given NEVER, which the emission test normally suppresses, rather than being skipped; skipping would differ in the rare state where nextEvent(u) is still NEVER.

The engine runs concurrently with grant emission and is architecturally optional: FR-12 requires that disabling it changes nothing but message volume, which DT-4 checks by running identical traces with the feature on and off and diffing the grant sequences.

Known hazard, inherited from the reference. Because DNET lets a federate stop sending NETs, a node's recorded nextEvent can lag behind lastGranted. In the C implementation this interacts badly with shutdown, producing a redundant grant that the guards suppress and stalling the federation one microstep short of the stop tag. The reference now avoids it in two ways, one per configuration: with no transient federates, a node whose upstreams are all disconnected is granted FOREVER (FR-14, the Phase 1 case); with transients, the grant is raised to at least maxStopTag once a stop tag exists (Phase 2). DT-5 shall include a shutdown-under-DNET scenario specifically.

7.8 Dispatcher and trace port

Collects up to n grants produced in one evaluation, serializes them into the outbound channels (one per federate, so in the common case they leave in parallel), and writes every accepted message and emitted grant to a trace FIFO as (cycle, kind, node, tag, provisional). The trace port is the primary verification instrument (FR-17): its records are compared directly against the software RTI's .lft traces.

7.9 Control plane (software)

Runs on a soft core or the host. Responsibilities, all off the critical path (D-5): load the topology and trigger closure recomputation; conduct the startup handshake and publish the common start tag; drive the stop protocol's bookkeeping and hand the final maxStopTag to the core; own diagnostics, error reporting, and trace drain; and, in Phase 2, implement transient admission — computing the five-way maximum for an effective start tag and writing the joining node's state before enabling it.

Integration with reactor-chisel goes through a port adapter (FR-20, D-11). At the integration baseline (reactor-chisel d94dd2d) three properties of that interface prevent driving it directly from this port:

  1. Tag representation. The hardware tag is a 32-bit unsigned scalar of nanoseconds with no microstep (Tag.scala). NEVER is Int.MinValue reinterpreted as unsigned, so it compares above FOREVER (Int.MaxValue) in unsigned comparisons, and the range ends about 2.1 s after the epoch.
  2. Grants above the next event. The scheduler asserts that a TAG greater than its NET, other than FOREVER, is not allowed (Scheduler.scala, line 48), whereas the decision of §7.5 grants the largest safe tag, which can exceed NET (the maximal TAG of §4.13 of the companion document).

In Phase 1 a hardware federate is consequently not a member of a zero-delay cycle, and the topology load rejects one that is; software federates receive PTAGs through their mailboxes (§8.2). 9.2 Throughput

The arbiter can take a control message into its input stage every cycle, but the sequencer accepts a new one only every I cycles (§7.2): I = Kmax − 4, or max(Kmax − 4, n + 1) with DNET enabled. The core has an unusual advantage: an executable, authoritative reference implementation exists. The strategy relies on it heavily — differential testing is the primary method, with directed and formal methods covering what randomization reaches poorly.

The steps of Figure 12

11.2 — Where the software coordinator’s variance comes from

KPI-2 tests whether the evaluation latency K is constant, and notes that the interesting result is the software tail. It is worth being specific about what generates that tail, because the sources are not interchangeable and only some of them are what people assume.

The assumed source, which is real but not the complete explanation: operating-system scheduling. Listener thread wake-up, condition-variable signalling, worker wake-up, preemption, migration between cores, frequency scaling. On a general-purpose kernel this has no upper bound, and it is usually the first cause suspected.

The structural source, which is more interesting: the coordinator’s latency is not a property of the request. Three couplings make it depend on factors the requesting federate does not control and cannot observe:

Coupling to other federates. One coarse lock serializes every listener thread, so the wait before your NET is even parsed is a function of how many other federates happened to speak at the same moment. Adding an unrelated federate to the federation changes the latency distribution of every existing one. The word for this is non-composable, and it is the same property that §10 of the companion document identifies as the reason PRET architectures exist.

Coupling to the data plane. Sharper, and largely undiscussed: because message forwarding holds the coordination lock across its entire chunked transfer, the tail of a grant latency is a function of the payload sizes other federates happen to be sending. A one-megabyte array crossing the federation blocks every decision in it for the duration. There is no semantic justification for this coupling — a grant does not depend on a payload — and it is invisible in any benchmark that uses small messages, which is most of them.

Coupling to protocol state. DNET makes an individual advance’s latency depend on downstream state: a federate whose NET is suppressed is not being answered late, it is not asking, and its own advance then waits on a data-plane message or on a later NET that clears the threshold. The in-transit clamp of §4.11 of the companion document has the same character — the recorded next event of a federate depends on traffic addressed to it. Both are correct. DNET is intended to reduce the number of decisions, and the in-transit clamp is a safety mechanism whose effect on the mean has not been measured; both make the distribution depend on the workload’s shape rather than on its rate.

Sources that are latent rather than observed deserve mention because a hang is readily misattributed: the RTI’s mutex is recursive by construction and the runtime waits on condition variables under it, a combination the source itself flags as dangerous; and, in a federation with transient members, grants are deferred into a queue drained against physical time, which may produce distinct latency regimes whose distributions should be measured separately.

Why variance is the quantity that matters, not the mean. In a centralized federation the grant lies on the critical path of every tag advance, so the lag between logical and physical time must absorb the worst round trip, not the average one. That lag is what a deadline clause is checked against, and in decentralized mode it is what the after > E + L + D inequality must cover. Coordinator jitter is therefore not paid in throughput; it is paid as either missed deadlines or a larger declared after, and a larger after is pipeline latency added to the application permanently, on every run, including the overwhelming majority in which the tail does not occur. A coordinator with a mean of 50 µs and a 2 ms tail costs the application 2 ms. This is the mechanism behind KPI-4, and it is the strongest form of the project’s claim: the result sought is not speed but a derived latency bound that supports the composition of timing budgets.

Measurement follows from that. Report distributions, not means: p50, p99, p99.9 and max over at least 10⁶ decisions, per configuration. Sweep the confounders deliberately rather than averaging over them — n, in-degree, competing CPU load, and payload size on unrelated connections, which is the coupling above and the one a naive benchmark will miss. PT-3 exists for that last case.

11.3 — Choosing the baseline

Two choices decide what KPI-1 means, and both should be fixed before M-4 rather than after the first favourable plot.

Which machine. The baseline is the C RTI on the same SoC’s CPU serving the same federation over the same CSR transport. Measuring instead against an RTI on another machine over TCP would inflate the result with a cost that NG-1 has already declared out of scope, and would answer a question that was not posed.

Which software. This point weakens the comparison and must be stated in the report rather than discovered by a reviewer. Part of the tail that §11.2 attributes to “software” is not intrinsic to software at all: the coupling between coordination and bulk data exists because one mutex covers both, and the reference source carries a FIXME saying each outgoing connection should have its own. A maintainer who fixed that would remove a large share of the tail without any hardware. The residue that remains — syscalls, scheduling, cache state, allocation, serialized fan-out — is genuinely structural, and it is still enough to carry the argument. So the accurate framing of the result is not “HW-RTI beats the current implementation” but coordination in fabric is bounded where coordination on a general-purpose CPU is a distribution. If time permits, measuring against a patched reference with per-socket locking would strengthen the baseline comparison; if it does not, the caveat belongs in the write-up.

Falsifiable expectation. If KPI-1 shows less than a 5× reduction in mean round trip in configuration C-A, the premise of §1.1 is wrong for on-chip use and the project should stop at M-4 rather than proceed to board bring-up. The go/no-go criterion is stated in advance deliberately.

14.2 Open questions for review

Table 32 — open questions.
IDQuestion
OQ-1Should Phase 1 target enclave coordination inside a single LF program rather than federate coordination? Enclaves use the same algebra with no transport at all, which would remove the reactor-chisel integration risk (R-6) entirely and could be the faster route to a demonstrable result.
Resolved, 17 September 2026: no. Phase 1 keeps federate coordination. The reasoning is recorded here because the question is a reasonable one and will otherwise be asked again.

The premise holds only in rti_common.c. The algebra is genuinely shared, but the enclave runtime discards half of what it computes. In rti_local.c, notify_provisional_tag_advance_grant is a log statement and notify_downstream_next_event_tag is empty, because zero-delay cycles between enclaves are prohibited; there is no in-transit accounting, since an enclave sending to another lowers the target's next_event directly; and there is no disconnection. Targeting enclaves would therefore leave FR-09, FR-10, FR-11 and FR-12 with no observable behaviour and FR-14 unreachable, taking DT-3, DT-4 and FV-3 with them. That is milestone M-4 in its entirety — four weeks whose exit condition is the KPI-1 go/no-go checkpoint. The proposal would therefore leave the KPI-1 go/no-go checkpoint, and requirements FR-09 to FR-12 and FR-14, without any configuration that exercises them.

The risk it would mitigate is already addressed, at lower cost. R-6's stated mitigation is to fall back to configuration C-C (CPU federates only), which has no reactor-chisel dependency and, unlike enclaves, preserves zero-delay cycles and therefore the whole PTAG and DNET requirement set. Moreover R-6 does not take effect until M-5: the differential campaign of §10.2 runs rti_common.c standalone against trace files, so M-0 through M-4 are already transport-free. Enclaves would offer no benefit during the phase they are supposed to accelerate.

And the trade runs the wrong way. Enclave mode minimises R-6 while maximising R-7 — the premise failing because coordination is not the bottleneck. The software baseline would become rti_local.c: a condition-variable signal inside one process, with no sockets and none of the chunked forwarding under the global lock (§4.12 of the companion document). What remains of the software cost is the coarse mutex and the enclave/RTI lock ordering. Beating that proves far less, and KPI-6 — the headline result — addresses a question that hardly applies to a coordinator already running in-process. A schedule risk costs weeks; a premise risk ends the project.

What is worth keeping from the question. An enclave-mode LF program is a zero-integration source of realistic traces and a smoke test at M-0 and M-2, precisely because rti_common.c is shared. Use it as an instrument, not as the target. If the pressure behind OQ-1 is schedule rather than risk, descope within the federate target — n ≤ 8 at M-4, runtime topology load (FR-16) deferred past M-6 — rather than adopting a target that deletes M-4. Revisit only if the goal changes from building a coordinator for hardware to publishing on the algebra, or if the reactor-chisel spike fails and C-C proves unavailable.

OQ-2Is bit-exact equivalence with the C reference (G-1) the right goal, or should the core implement a cleaner algebra (e.g. uniform tag-typed delays, eliminating the interval/tag dual encoding of §6.1) and accept a documented divergence? The former eases verification; the latter yields better hardware.
OQ-3How should the core behave if a federate violates the protocol (NET below lastGranted)? The reference tolerates staleness because of DNET; hardware could instead flag it as a hard error. FR-18 currently assumes an allowance whose width is unspecified.
OQ-4Is MSG_SENT (§7.1) necessary, or can the sending federate's own NET updates carry the same information? Removing it would simplify the federate-side contract at some cost in grant tightness. Keeping MSG_SENT raises a second question — whether one minInTransit register per node suffices, or whether a small per-node queue is needed for several outstanding messages at distinct tags.

OQ-5Should the trace port emit LF-compatible .lft records directly, so existing LF tracing tools work unmodified against a hardware coordinator?
OQ-6How many EIMT read ports (P_EIMT) should the first build use, and which goal gives way? On the estimates of §5.2, at n = 16 no setting meets both G-2 and G-5: one port misses G-2 by a cycle and G-5 at 21%; two ports meet G-2 at 28%. With a single EIMT tree (P_EIMT = 1) the estimates give K = 24 cycles and about 7.0k LUT, 13% of a Zynq-7020, so G-2 and G-5 hold together without relaxing either, and both are now stated at n = 8. OQ-7Would a decentralized realization — local advance with a waiting bound W, as in micro-LF, with E = 0 and L and D bounded statically — suffice for the federations Phase 1 targets?
