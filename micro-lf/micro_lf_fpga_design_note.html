§ 1

Purpose and principal conclusion

A practical FPGA extension of micro-LF should begin with a federated input engine that accelerates message admission, per-connection state access, tag comparison, and event delivery while retaining reaction bodies in software. This architecture is technically plausible, and the advancement policy it must reproduce has now been traced in reactor-uc at commit df7cfea (§5, §9). Cycle-accurate RTL can claim semantic equivalence only after the differential checks of §9, and only for behaviour the design deliberately adopts: three runtime behaviours found while tracing are questionable and should be decided, not copied (§4, §5).

micro-LF is the embedded Lingua Franca environment; reactor-uc is its runtime [6]. Communication between reactors on different microcontrollers passes through federated connections and a NetworkChannel implementation. Transport selection and logical-time coordination are distinct design decisions. Replacing a transport does not by itself introduce an RTI or replace the scheduler.

The note consolidates the communication and FPGA discussions into a design basis for future tutorial and HW-RTI specification material. The HW-RTI comparison uses the project architecture described in those discussions: centralized state, topology-dependent coordination, and TAG or PTAG grants. It is an architectural comparison rather than a register-level assertion about a particular implementation.

Evidence and design status

Interface observations are supported by public reactor-uc API documentation [2–5]. Backend execution details recorded in the conversation are identified as discussion findings where their exact current implementation remains to be traced. Proposed hardware blocks, descriptors, and interfaces are design proposals. SAFE, WAIT, TARDY, and EVENT are conceptual result labels, not established reactor-uc API constants. This revision traces the open items in the source at commit df7cfea [7]. Statements marked “Traced” cite file and lines at that commit; the backend details of §3 were not traced and remain discussion findings.

Corrections that constrain the design

UART, CoAP/UDP/IP, and S4NoC are alternative channel implementations, not TCP emulation. Protocol Buffers are not mandatory for application port values. last_known_tag and max_wait are not a complete STP equation. Hardware arbitration can replace selected software locks only when ownership and atomicity are explicitly preserved. A hardware transport adapter is not automatically a hardware RTI. Traced, the decision is: an input is resolved at a candidate tag g when last_known_tag ≥ g; otherwise the federate waits until its clock reads g.time plus the largest max_wait among the unresolved inputs (§5).

§ 2

Communication between federates

A federate is a runtime participant containing reactors and their local execution state. A connection crossing a participant boundary must preserve the association between the source value, destination connection, and logical tag. The physical link moves bytes or words; the runtime interprets their logical meaning.

A FederatedConnectionBundle groups inputs and outputs associated with one remote federate and holds a NetworkChannel pointer, serialization hooks, a send-message object, sizes, and an index. Multiple LF connections can therefore share one peer channel. The connection identifier must select the correct destination within that peer association [3].

An implementation should not allocate one TCP socket per LF port merely because ports are distinct. Conversely, conn_id alone should not be assumed globally unique. A hardware table may require the pair {bundle_id, conn_id}, translated to a compact local connection index during admission. Traced: conn_id indexes the inputs array of the receiving bundle (federated.c, line 185), so it is local to one peer association and the pair {bundle_id, conn_id} is the correct key.

NetworkChannel contract

The interface sends a FederateMessage and exposes connection establishment, state queries, closure, receive-callback registration, and cleanup. It supports asynchronous and polled operation; the polled variant adds poll(). expected_connect_duration describes connection setup expectations rather than an application message latency bound [2].

send_blocking() is a completion-oriented software contract. A FIFO write by a hardware adapter is not automatically equivalent to its return semantics: the adapter must define when a message counts as sent and how failure is reported. Receive callbacks should feed runtime scheduling rather than execute arbitrary reaction bodies in interrupt context.

Transport and policy independence

A proposed HwLinkChannel can implement the existing abstraction over MMIO, FIFOs, DMA, or a NoC endpoint. This is a transport integration point. Local advancement, input knowledge, physical-time waiting, and tardiness handling remain separate semantic responsibilities until explicitly moved across the hardware/software boundary.

§ 3

Backend realizations and execution context

Table 1 — channel backends and their design implications.
BackendPathDesign implication

The public channel header enumerates these four backend types and conditionally selects platform implementations [2]. The conversation associated TCP/IP with POSIX and Zephyr, UART with RP2040/Pico, CoAP over 6LoWPAN with RIOT, and S4NoC with Patmos. These associations describe discussed configurations, not an exhaustive current support matrix.

UART and asynchronous reception

The investigation described a UART connection-establishment protocol that can send replies from asynchronous reception context. On bare-metal targets, reception may occur in an ISR. A hardware front end therefore needs more than a shift register: it needs message delimitation, validation, connection-state handling, and a defined transfer into the runtime. Exact framing, recovery, and callback execution rules remain implementation-specific. Not traced in this revision.

CoAP and critical sections

The conversation recorded a CoAP send path that must keep interrupts operational while waiting for an acknowledgement. Holding a critical section across that operation can prevent the very progress required for completion. An accelerator must preserve this progress dependency rather than treating every backend as a synchronous socket wrapper. Not traced in this revision.

S4NoC and FPGA relevance

Patmos/S4NoC provides an existing architectural precedent for federation over on-chip communication. It motivates an FPGA or SoC implementation without adding TCP/IP. It does not establish that a proposed custom endpoint is wire-compatible with the existing backend or that coordination already executes in RTL.

Transport properties to retain

Ordering, delivery failure, duplicate handling, retry behavior, maximum message size, and connection loss must be documented for the selected backend. A common NetworkChannel API does not imply identical reliability or latency across implementations. These properties affect what a receiver may infer from incoming tags and what waiting policy can safely assume.

§ 4

Messages and serialization boundaries

The runtime-facing communication object is FederateMessage. TaggedMessage is the tagged-data object accepted by the federated input scheduling interface. Hardware should distinguish the federation message envelope from application payload bytes and from the transport framing around the message [2,3].

The serializer hook accepts a value pointer, its size, and a message buffer, and returns a serialized length. The deserializer accepts a destination value pointer, serialized bytes, and message size. The documentation identifies raw copying as the default and permits custom serializers including Protocol Buffers [4]. Thus, the existence of nanopb and generated message definitions in network_channel.h does not imply that every port value is encoded with protobuf. Traced: the FederateMessage envelope itself is always nanopb-encoded, and message.proto bounds the TaggedMessage payload at 832 bytes, which fixes the largest serialized port value a hardware buffer must hold.

Raw copying is appropriate only with an agreed representation. Endianness, structure padding, type sizes, alignment, and pointer-containing values need explicit treatment when peers have different ABIs. A custom codec can provide a portable representation, but it adds its own size bounds and failure cases. The accelerator must not reinterpret opaque application bytes unless that representation is part of the hardware contract.

Payload ownership and event metadata

A first implementation can keep application deserialization in software while hardware parses transport metadata and stores payload bytes. A later design may offload fixed, bounded codecs after profiling. Protocol-envelope decoding and application-value decoding should remain independently selectable.

The proposed descriptor {tag, connection_id, payload_pointer} is a compact starting point, not a sufficient reproduction of the runtime event layout. event.h also distinguishes ordinary and system events and retains an intended_tag for STP violation detection [5]. Hardware descriptors may consequently need scheduled_tag, intended_tag, event kind, payload length, and a trigger or handler mapping.

The payload pointer should be a bounded buffer handle or offset, with allocation, commit, consumption, and release states. Payload storage must remain live through deserialization and reaction consumption. Traced (federated.c, lines 207–258): when the payload pool is exhausted, the message is dropped and last_known_tag is left unchanged. When deserialization fails, or the event cannot be scheduled (event queue full, tag after the stop tag or before the start tag), the event is dropped but last_known_tag still advances to its tag, so the input counts as resolved at a tag whose value was lost. On those paths the allocated payload slot does not appear to be released, since release happens only when an event is prepared; this needs confirmation. A hardware design should decide these behaviours rather than reproduce them: advancing knowledge only together with a committed event is the safer contract.

§ 5

Input knowledge and local advancement

The inspected FederatedInputConnection contains delay, type, last_known_tag, max_wait, payload_pool, conn_id, a mutex, and a scheduling function. type distinguishes logical from physical connections. max_wait is stored as instant_t while the constructor accepts interval_t; this deserves implementation tracing rather than an assumption that the member is already an absolute deadline [3]. Traced: acquire_tag adds max_wait to the candidate tag’s time (it waits until next_tag.time + max_wait; federated_environment.c, lines 88–121), so the stored value is an interval despite its instant_t type.

last_known_tag tracks the extent of knowledge for an input, not simply the most recent physical arrival timestamp. Traced, it has two writers. On reception it is raised, under the connection mutex, to the message tag after lf_delay_tag applies the connection delay; for a physical connection the base is the receiver’s physical time (federated.c, lines 190–256; failure cases in §4). When a neighbor that joins a running federation announces its joining time, the startup coordinator sets it to that time (startup_coordinator.c, lines 492–509). That loop indexes inputs[i] with the bundle index instead of inputs[j], writes without the mutex and can lower the field: an apparent defect, to be reproduced and reported upstream. There is no absence message; an order-preserving channel and tag-monotone sending make a received tag a lower bound on later tags of that connection. The conversation first referred to InputPort.last_known_tag in concurrency discussions; the later concrete header places the field in FederatedInputConnection. These references should not be merged into a single unverified object layout.

Tag ordering

For ordinary finite tags g = (t, m), ordering is lexicographic: g1 < g2 when t1 < t2, or when t1 = t2 and m1 < m2. A time comparator, equality test, and microstep comparator implement this relation. Exact signedness, widths, sentinel values, and overflow behavior must follow the runtime definitions.

Waiting and tardiness

The discussion established max_wait as the per-input waiting allowance for that input to become known at a candidate tag. Traced (schedulers/dynamic/scheduler.c, main loop; federated_environment.c, lines 88–121): the scheduler selects the next event tag g, waits until physical time reaches g.time and then calls acquire_tag(g). For every input on a connected channel with last_known_tag < g it takes the largest max_wait W and waits until physical time reaches g.time + W. An arriving message interrupts the wait and the scheduler restarts the selection, possibly with an earlier tag, against the same absolute deadline. Inputs on disconnected channels are skipped. Physical time is the clock-synchronized timescale, and the wakeup is converted to hardware time when the wait starts, so a clock adjustment during a wait takes effect only at the next wakeup. A candidate-tag decision depends on input knowledge, connection delay and type, physical time, and runtime scheduling state. The shorthand last_known_tag + max_wait -> STP is therefore inadequate.

An expired wait allows a policy-specific action; it does not prove that a remote message can no longer arrive. Tardy detection must preserve the distinction between the intended tag and the tag at which an event is actually scheduled. Traced: schedule_at rejects any tag at or before the current tag, equality included (scheduler.c, from line 406). The receive path then reschedules the event at the current time with the microstep increased by one and keeps the original intended_tag (federated.c, lines 225–233). When that tag executes, a reaction triggered by or observing a present port whose intended_tag differs from the current tag runs its tardy handler instead of its body if it has one (scheduler.c, lines 147–182); otherwise the body runs on the late value and the runtime logs a warning.

With several logical inputs, any reduction to one local readiness result must follow the scheduler’s treatment of all relevant inputs. Traced: the reduction is the maximum of max_wait over the unresolved inputs. acquire_tag does not distinguish physical from logical inputs, and the compiler gives both the same default, forever; how a physical input with that default behaves was not tested and belongs in the differential traces.

§ 6

Centralized and distributed coordination

In the HW-RTI architecture discussed for the project, a central engine maintains federation-wide coordination state and uses topology information to generate advancement permissions. LTC denotes logical-tag completion, NET denotes next-event-tag information, TAG denotes a tag-advance grant, and PTAG denotes a provisional tag-advance grant. Provisional and final grants have distinct semantics and must remain distinct in hardware.

The proposed reactor-uc accelerator instead operates beside each federate and retains per-input state. Its local output helps that federate decide whether to wait, admit an event, or proceed under the selected decentralized policy. It does not derive a centralized grant merely by renaming last_known_tag as LTC.

Table 2 — centralized and distributed coordination compared.
DimensionCentralized HW-RTIDistributed reactor-uc acceleration
PlacementShared federation coordinatorEngine beside each federate
State scopeFederate progress and topologyInput knowledge and connection parameters
Typical inputsLTC, NET, topology and completion stateTagged data, local candidate tag, physical clock
Typical resultTAG or PTAG permissionLocal readiness and event or tardiness result
Main proof burdenGrant safety and topology dependenciesInput knowledge, timing and admission equivalence
Scaling pressureCentral state and arbitration bandwidthReplicated engines and local input count

Peer-to-peer describes who exchanges messages; decentralized coordination describes where advancement decisions are made. Neither term excludes a shared clock service, startup mechanism, or other common infrastructure. Timing assumptions remain necessary when local progress relies on bounded waiting. Traced for reactor-uc: there is no RTI. Startup computes a maximum over neighbors in a fixed number of rounds (the compiler’s longest-path count, obtained by two breadth-first sweeps, exact for trees); with clock synchronization enabled only the grandmaster proposes a start time. Clock synchronization follows a grandmaster designated by @clock_sync(grandmaster=true), each federate synchronizing with the neighbor closest to it; shutdown announcements are forwarded among neighbors.

A common library of tag comparators, RAM controllers, arbitration, and descriptor queues may serve both architectures. A configurable policy engine is a research option, but central and local policies require different state and interfaces. Reuse of primitives does not demonstrate equivalent correctness or a drop-in substitution between HW-RTI and HW-STP, a hardware realization of one federate’s safe-to-process decision, that is, of acquire_tag and the late-message path.

§ 7

FPGA implementation candidates

Two implementations must be separated. Hosting software reactor-uc instances on soft or hard CPUs inside an FPGA preserves software coordination and mainly supplies processors, memory, timers, and interconnect. Runtime acceleration moves selected state transitions and data handling into programmable logic. Only the latter introduces the proposed federated input engine.

Resource and latency tradeoffs

Connection RAM naturally maps to BRAM for larger configurations; registers may be preferable for a few inputs. A shared comparator scanning N inputs saves logic but introduces a scan latency and requires a consistent state snapshot. Parallel comparators reduce latency at the cost of resources and reduction logic. Neither choice has a quantified benefit until the workload and clock target are measured.

For illustration, 32 rows with three 64-bit fields (delay, tag time, and wait parameter), a 32-bit microstep, and an 8-bit type consume 928 bytes before validity bits, alignment, indexing, or additional scheduler state. These widths are budgeting assumptions, not a confirmed runtime ABI.

Event queue architecture depends on ordering semantics and required throughput. A FIFO is insufficient if later arrivals can have earlier admissible tags. A heap, sorted structure, or bounded bucket scheme must preserve the software ordering and same-tag behavior. Metadata can be queued separately from payload RAM to reduce copying, provided handles remain valid.

Preallocated software storage [1] motivates bounded hardware pools; it does not remove capacity analysis. Queue-full and payload-full behavior require explicit backpressure or a defined failure path. Offloading a comparator alone may have little effect when transport, copying, or reactions dominate execution time.

Value hypothesis

In decentralized coordination the latency of an advance is dominated by physical time: a federate with an unresolved input waits until g.time + W, and W is a timing assumption chosen by the programmer. The readiness test itself is a short loop of tag comparisons over the federate’s inputs. Accelerating that test cannot shorten W. The HW-RTI case is different, because there the dominant cost is the serialized fan-out of grant decisions, which hardware evaluates in parallel.

Where the proposed engine can plausibly help: the latency and jitter between a frame’s arrival and its admission (interrupt service, framing, copying), the CPU occupancy of reception on small cores, and the predictability of admission timing, which narrows the latency bound that W must cover. Each is a hypothesis to measure on the target before RTL beyond the front end is built: the arrival-to-admission latency distribution, ISR and critical-section length, CPU time per message, and the smallest W that produces no safe-to-process violations at a given load.

Relation to the HW-RTI specification: its OQ-7 asks whether a decentralized realization with zero clock error and statically bounded latency and sender lag suffices on chip [8]. Measurements from the first stages of §10 (software-only federation over an on-chip link, then front-end offload) would provide evidence for that question. The accelerator itself remains a project separate from HW-RTI.

§ 8

Proposed hardware and software boundary

Software initially owns application initialization, connection configuration, generated port mappings, custom codecs, reaction scheduling dependencies, reaction bodies, and exceptional recovery. Hardware owns only the state explicitly assigned to it. A mirror in software is diagnostic unless a coherent update protocol gives it authority.

Atomic admission and arbitration

The accelerator must arbitrate receive updates, candidate-tag queries, CPU configuration, and event consumption. One possible admission transaction reserves storage, validates identifiers and lengths, writes payload and descriptor metadata, and commits the state visible to the scheduler. The exact knowledge-update point must follow the software semantics; readiness must not become visible before the associated event is committed.

The conversation suggested that mutexes could disappear. More precisely, a hardware-owned state region may replace a software mutex with an arbiter and atomic commit rules. Concurrency remains at the CPU boundary, between clock domains, and during DMA or reset. Memory ordering, cache maintenance, simultaneous timeout and arrival priority, and multiword snapshot consistency must still be defined.

Adapter interface proposal

Useful commands include configure connection, submit candidate-tag query, enqueue transmission, consume event, release payload, and reset. Responses can carry request IDs, connection or event handles, status, and a state version. Interrupts should signal committed results and errors; level-triggered or counted notification avoids losing events during service. These are interface proposals, not existing register assignments.

Clock-domain crossings need synchronizers or asynchronous FIFOs. A physical-time snapshot must be coherent across words. Updating or synchronizing a clock can invalidate a cached deadline; the selected policy must define how such changes affect pending waits. Reset must quiesce transactions and reclaim buffers without exposing stale descriptors.

§ 9

Verification required before cycle accurate RTL

The next design step is to freeze a repository commit and platform configuration and extract a software transition model. Headers establish the interface and state but cannot define all transitions. The following checks are necessary before naming the design an implementation of the reactor-uc advancement policy.

Status after tracing

Resolved at df7cfea: the known-at predicate (last_known_tag ≥ g); the reduction over inputs (maximum of max_wait over unresolved inputs on connected channels); max_wait as an interval; the absolute deadline under interruption; the violation predicate, equality included; rescheduling at microstep + 1 with intended_tag preserved; tardy dispatch; every write to last_known_tag; the conn_id namespace; the payload bound; and the absence of any absence message.

Open: physical connections under the default max_wait; the questionable behaviours of §4 and §5 (knowledge advancing after a dropped event, payload release on failure paths, the joining-time write); UART and CoAP backend details (§3); the effect of clock adjustment during a wait on each platform; the startup round count on cyclic neighbor graphs; and concurrency between interrupt context and the scheduler on each platform. The checks below remain the plan for these items and for the differential campaign.

Scheduler and wait policy

Trace candidate-tag selection, the exact known-at predicate, all input iterations, conversion of max_wait to a physical deadline, wakeup and timeout behavior, and the distinction between logical and physical connections. Determine startup, shutdown, stop-tag, and disconnected-peer behavior.

Message and tag updates

Trace the receive callback, dispatch, scheduling function, message schema, and every write to last_known_tag. Establish delay application, zero-delay microsteps, ordering assumptions, absence or control-message effects if present, duplicates, and malformed-message handling.

Tardiness and event semantics

Extract intended-tag preservation, STP violation handling, equal-tag insertion, event and system-event interaction, payload allocation and release, and queue failure behavior. Determine which scheduler state is required beyond the connection table.

Concurrency and platform time

Map all critical sections, ISR and worker contexts, callback reentrancy, send paths, physical clock operations, clock synchronization, and interrupt progress dependencies. Define the atomic ordering of an arrival against a simultaneous readiness query or timeout.

Representation and generated configuration

Confirm tag widths, signedness, sentinels, overflow rules, message lengths, serializer contracts, connection ID namespaces, bundle mapping, static capacities, and the generator’s parameter initialization.

Equivalence and measurement plan

Build differential traces against the frozen software model: multiple inputs with different knowledge tags, equal-time microsteps, zero and nonzero delays, physical connections, expiry-boundary arrivals, out-of-order or duplicate traffic where applicable, pool exhaustion, queue saturation, reconnect, reset, and clock changes. Check event order, payload ownership, knowledge updates, readiness results, and violation reporting, not merely throughput.

Measure end-to-end latency, maximum interrupt or critical-section time, CPU occupancy, event and payload capacity, sustained traffic, FPGA resource use, and clock frequency. Compare software on FPGA CPUs, transport-only offload, and progressively deeper admission or scheduling offload under the same workload. Performance improvements remain hypotheses until measured.

§ 10

Recommended development sequence

First, establish software-only federation over the selected on-chip or external link and verify NetworkChannel adapter semantics. Second, offload framing and bounded payload movement while keeping scheduling policy in software. Third, add connection-state access and tag comparison with differential checks. Fourth, implement timing and tardiness logic only after the scheduler model is complete. Finally, consider event queue offload when profiling shows sufficient benefit and ordering equivalence is demonstrated.

This progression makes each boundary independently reviewable. It also preserves the option to reuse primitives in HW-RTI without prematurely forcing centralized grants and decentralized waiting into the same protocol. Reaction bodies should remain on the CPU in the initial design; their synthesis would be a separate research problem.

Material for future tutorial and specification integration

The tutorial can adopt the layered communication model, backend distinctions, serializer correction, and side-by-side architecture explanation. The specification can later adopt a verified transition model, ownership contract, bounded descriptor format, error behavior, and timing interface. A cycle schedule and register map should follow those semantics rather than substitute for them.

The local advancement function is now traced (§5, §9); the unresolved points are the behaviours the hardware should adopt where the software is questionable, and whether acceleration pays (§7, Value hypothesis). The available structures support a credible federated input engine, but they do not yet establish a complete HW-STP specification. The design should retain this qualification until equivalence validation and the measurements of §7 close it.
