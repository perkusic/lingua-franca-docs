§ 01 / motivation

Why Lingua Franca exists

Cyber-physical systems — robots, vehicles, industrial controllers, sensor-fusion pipelines — have a property that ordinary software can largely ignore: when a computation happens is part of whether it is correct. A fusion filter that consumes an accelerometer sample and a wheel-encoder pulse in the wrong order does not produce a slightly stale answer; it can pass through physically inconsistent states and produce serious estimation errors. NASA attributes an in-flight anomaly on the Ingenuity Mars helicopter to exactly this class of bug: a single lost camera frame caused every subsequent image to be processed with the wrong timestamp[15].

Yet the dominant tools for building such systems do not, by themselves, provide the timing and ordering guarantees that such reasoning requires. Of threads with shared memory, Lee writes that, “as a model of computation, [they] are wildly nondeterministic, and the job of the programmer becomes one of pruning that nondeterminism”[2]; locks perform the pruning, and nothing in the model checks that it is complete. Publish–subscribe middleware (ROS 2 and the Data Distribution Service, DDS) replaces data races with message races: delivery order depends on scheduling and on variation in network delay. Testing exercises a small fraction of the possible interleavings, and an erroneous interleaving may not be among them.

Lingua Franca (LF) is a polyglot coordination language built on the reactor model of computation[1],[3]. The bet is different from inventing a new programming language: your actual computation stays in C, C++, Python, Rust, TypeScript — LF adds only a thin syntax for composition, and in exchange the composition acquires mathematical properties:

Determinism by default. Given the same initial state and the same sequence of tagged inputs, a well-formed reactor program whose reaction bodies are deterministic has exactly one legal behavior. Under those assumptions concurrency is no longer a source of nondeterminism: parallel execution on many cores, or distributed execution on many machines, does not change the logical behavior the program specifies[18]. Inputs that come from physical time, and the handling of timing violations, require the further conditions discussed below.

Time as semantics, not side effect. In C there is no portable way to express “do this at exactly t”; timing is an accident of the platform. LF gives every event a tag on a logical timeline, relates that timeline to physical clocks in four disciplined ways, and lets you state deadlines that the runtime checks, invoking a violation handler when one is missed.

One abstraction, every scale. The same program text runs single-threaded, multi-threaded, distributed across a network (a federation), or — the deep end of this document — partly as software and partly as synthesized digital logic on an FPGA (field-programmable gate array), and eventually on processors designed so the timing assumptions are theorems. Each scale reuses the same coordination contract, and the rest of the document follows that one contract through these four settings.

1.1 — From actors to reactors: message ordering and determinism

One of the models reactors grew from is the actor model, introduced by Hewitt, Bishop and Steiger in 1973[41] and developed by Agha into a foundation for concurrent computation in distributed systems[42]. An actor keeps local state that no other actor can touch; actors communicate only by sending each other messages asynchronously; and an actor’s behaviour is its response to a message — update its state, send messages, create further actors. With no shared memory there are no data races.

That removes one source of nondeterminism, not every source. An actor that processes one message at a time still has to take some message next, and processing them one at a time does not determine which. Four orders are worth keeping apart: the order in which messages are sent, the order in which they arrive, the order in which the receiver selects them, and the order in which their processing takes effect. Guarantees about any of these belong to a particular model or implementation. Many actor systems preserve order from one sender to one receiver, but first-in-first-out delivery per pair implies nothing about the relative order of messages from different senders, and mailbox policies — FIFO, priorities, selective receive by pattern — differ from one system to another; there is no single policy that all actor systems share.

A small example makes the point. An actor holds x = 1; two independent producers send it A, “increment x”, and B, “multiply x by two”.

The steps of Figure 1

  4. Processing. C takes the front message, updates x, then takes the next: 1 → 2 → 4 in execution 1 and 1 → 2 → 3 in execution 2. Each message is handled whole, no update is lost, and the results still differ.

What Figure 1 shows. There is no shared memory and no lost update, and still two outcomes: the order of arrival, which nothing in the program fixes, decides the result.

This is not a verdict on actors. An actor program can be deterministic when an order is imposed: by a protocol that sequences the messages, by restrictions on who may send to whom, or by operations whose order does not matter. Commutative operations — two increments, say — make the final state independent of order, but not necessarily everything in between: which intermediate value an observer sees, or which messages are sent along the way, can still depend on it. Lee, Neuendorffer and Wirthlin make the wider distinction: actor-oriented design, components that interact only through ports, is a way of structuring systems, and the model of computation that governs the components — dataflow, discrete events, synchronous-reactive and others — decides how they execute, determinism included[43].

Reactors keep the actor’s structure — encapsulated state, behaviour as reactions to messages, no shared memory — and add the order the example lacks[1],[3]. From discrete-event systems they take tags: every event carries a logical time, and events are processed in tag order. From synchronous languages they take simultaneity with an explicit order: at one tag, reactions run in an order fixed by the dependencies in the program and, inside one reactor, by the order in which reactions are declared (Section 2). Give a reactor two input ports, send the increment to one and the doubling to the other at the same tag, and declare the incrementing reaction first: every execution computes 1 → 2 → 4. Declare the doubling first and every execution gives 3. Either way the program chose, not the scheduler. The program Levels.lf in the tutorial’s examples/ folder prints the same rule at work.

What Figure 2 shows. Nondeterminism does not need shared memory — an order left open is enough — and the reactor closes it in the program text.

What the reactor guarantee covers, and what it does not:

  • Same inputs, same tags. Two executions are compared when they receive the same input events with the same tags, and the reaction bodies are deterministic themselves — no clocks, random numbers or unsynchronized outside state read inside them.
  • Physical actions are inputs. A physical action is stamped with the physical time at which it happens, so two runs of one program usually give it different tags; the guarantee is relative to those tags.
  • Tags before declarations. Declaration order decides only among reactions at the same tag; an event with an earlier tag is processed first, whatever the order of declaration.
  • Terminal output is not evidence. The order in which lines from several processes appear on a terminal reflects output buffering and operating-system scheduling, not the logical order of events. It proves neither determinism nor its absence; tagged records, such as the traces of Section 14, are what to compare.
  • Waiting is local. The scheduler does not wait for every input of the whole program before running anything: a reaction runs as soon as everything it depends on at the current tag is known, present or absent (Sections 2, 8).

§ 02 / foundations

The reactor model in brief

A reactor is a stateful, concurrent component with typed input and output ports, private state variables, timers, actions, and reactions — event handlers whose bodies are written in the target language. Reactors compose by connecting ports; connections may carry a declared after delay. The unit of communication is the event: a value plus a tag (t, m), a logical timestamp t and a microstep m ordering logically simultaneous rounds (superdense time).

Three rules give the model its power. First, a reaction is invoked only when every event it could observe at the current tag is known — present or provably absent. Second, reactions within one reactor execute in declared order at any shared tag, so shared state never races. Third, in the default execution mode (without the fast target property), logical time is not allowed to advance ahead of physical time, and physical reality enters only through disciplined gates: startup synchronization, physical actions (asynchronous events stamped with current physical time — the interrupt/sensor entry point), and deadlines bounding the lag between the two timelines.

One derived notion is used constantly further down and is worth naming here: the level. The compiler topologically sorts every reaction in the program by the dependencies among them, and a reaction’s level is its rank in that order — a reaction may fire only once every reaction that could feed it, directly or transitively, has had its chance at this tag. Within a tag the runtime therefore executes level by level. That granularity is what later lets a federate begin work at a tag whose network inputs are not all resolved yet: every reaction whose level is lower than that of the first reaction reading an unknown port may run, and execution stops precisely at that level (Section 8).

If in2 is a network port whose status is still unknown, reaction 1 may nevertheless run to completion at this tag; reaction 3 may not, and neither may any reaction at a higher level. That is the mechanism Section 8 calls the maximum-level cap.

Everything else in this document is one question asked at four scales: how does a component earn the right to advance to a tag — that is, to conclude that no earlier-tagged input can still arrive?

§ 03 / distribution

Federations and the RTI

A distributed LF program is a federation: each top-level reactor instance becomes a federate, compiled into its own executable, deployable on its own machine. Alongside them runs the RTI (Run-Time Infrastructure), a separate program — C source in reactor-c/core/federated/RTI, bundled and compiled automatically with your program since LF 0.10.0 — that coordinates startup and shutdown, runs clock synchronization, and, under the default centralized coordination, regulates every federate's advancement of logical time and brokers every inter-federate message. The name and the architecture are deliberate homage to the High-Level Architecture (HLA) of distributed simulation[6], adapted for real deployments where logical time is bounded by physical time and actions cannot be rolled back.

3.1 — Starting and stopping a federation

Every run begins with a startup protocol and ends with a stop protocol, and in both the federates must agree on one tag.

Startup: max-of-proposals plus a margin. Each federate proposes a start time (its current physical clock) in a TIMESTAMP message. The RTI blocks until every persistent federate has proposed, takes the maximum, adds the fixed DELAY_START margin — one full second in the current source, which is worth knowing before you wonder why a two-federate program takes a second to print anything — and broadcasts that as the common start tag. The maximum is what prevents a federate whose clock is ahead from being asked to start in its own past; the margin covers the broadcast itself, so that no federate is already late when it arrives.

Three implementation facts make that paragraph precise. First, the quorum counts persistent federates only: the RTI waits for number_of_scheduling_nodes − number_of_transient_federates proposals, and a transient that happens to arrive during startup is folded into the same computation rather than counted toward it. Second, the wait is a condition variable, not a poll: every federate’s own socket thread blocks on received_start_times, the last one to propose broadcasts, and each thread then sends the start tag on its own socket — there is no single broadcast loop. Third, the RTI is a three-state machine, startup_phase → execution_phase → shutdown_phase, and the phase is what decides the answer to a late arrival: in the execution phase a persistent federate is rejected outright with JOINING_TOO_LATE, while a transient is admitted through the effective-start-tag computation of Section 3.2. Membership is fixed at startup; only transience was ever negotiable.

One synchronization detail outlives startup and will matter in Section 4. A federate whose start tag has not been sent yet is in state PENDING, and every path that would write to it — a TAG, a PTAG, a DNET, a forwarded message — first blocks on the sent_start_time condition variable until the state leaves PENDING. Nothing reaches a federate before its start tag does.

The steps of Figure 5

  1. FED_IDS. A opens a TCP connection to the RTI (port 15045 by default) and sends its federate ID and the federation ID that the launcher gave every process. The RTI accepts persistent federates one at a time and finishes each handshake before accepting the next; when it runs with -a, an HMAC exchange comes first.
  2. ACK or REJECT. The RTI checks that the federation ID matches its own and that the federate ID is in range and not already in use, then answers ACK — or REJECT with a cause such as FEDERATION_ID_DOES_NOT_MATCH or FEDERATE_ID_IN_USE. A federate that reached the wrong RTI tries again.
  3. NEIGHBOR_STRUCTURE. A lists its upstream federates, with the minimum delay on each connection, and its downstream federates. That is everything the RTI will ever know about the program (Section 7); the min-delay matrix of Section 4.5 is built from these messages.
  4. UDP_PORT and initial clock synchronization. A declares whether, and on which UDP port, it takes part in clock synchronization. If the RTI runs with initial synchronization (-c init, which the launcher passes), it exchanges timestamps with A over this same socket, ten rounds by default (Section 6). Only then does it start a thread dedicated to A and go back to accept the next federate.
  5. B, the same way. Steps 1–4 repeat for B, and for every other persistent federate.
  6. TIMESTAMP(t_A). A proposes its current physical time as the start time and blocks until the answer arrives. A’s thread at the RTI records the proposal, keeps the largest one seen so far, and waits on the condition variable received_start_times.
  7. TIMESTAMP(t_B). B’s proposal is the last persistent one: its thread wakes the waiting threads, and the RTI moves from the startup phase to the execution phase. From now on a persistent federate that tries to join is rejected with JOINING_TOO_LATE; a transient one is admitted through Section 3.2.
  8. the start time. start_time = max(t_A, t_B) + DELAY_START, with DELAY_START one second in the current source. The maximum keeps a federate whose clock is ahead from being asked to start in its own past; the margin covers the delivery of the answer.
  9. TIMESTAMP(start_time). Each federate’s own thread sends the start time on that federate’s socket — there is no broadcast loop — and moves its state from PENDING to GRANTED. Until then no TAG, PTAG, DNET or forwarded message may be written to it. The federate unblocks and starts at tag (start_time, 0).

What Figure 5 shows. No federate learns the start time until every persistent federate has proposed one, and nothing else reaches a federate before its start time does.

Shutdown: two-phase, at the latest proposal. Any federate (or a timeout, or Ctrl-C) can send STOP_REQUEST with a proposed stop tag. The RTI forwards the request to every other federate; each replies with STOP_REQUEST_REPLY carrying its own proposal, which may be later if it has work already committed. The RTI keeps the running maximum, and once every federate has replied broadcasts STOP_GRANTED with that max_stop_tag — clamping each federate's next event to it, so the whole federation halts at one agreed tag rather than tearing at different points on the timeline. A single flag — stop_in_progress — prevents concurrent stop requests from racing, and a second, requested_stop per federate, makes the counting idempotent.

Three edges are worth knowing because they are where a shutdown hangs. The quorum again excludes transients: the RTI broadcasts once num_scheduling_nodes_handling_stop reaches the persistent count, so a transient that never replies cannot wedge the federation, and a federate already NOT_CONNECTED is counted as having replied the moment the request would have gone out to it. A federate that is still connected but silent can wedge it, which is why the first stop request also spawns a timeout thread: it wakes in thirty slices of MAX_TIME_FOR_REPLY_TO_STOP_REQUEST — thirty seconds in the current source, so one second per slice — and if the grant has still not been broadcast by the last one it prints how many replies arrived and exits the RTI outright. A coordinator that cannot coordinate stops the program rather than hanging it — the same philosophy as the unclean-death rule below. And the broadcast does not only announce the tag: as it walks the federates it clamps each one’s recorded next_event down to max_stop_tag, so the grant algebra of Section 4 cannot subsequently prove something safe beyond the point where the federation has agreed to end.

Departure and failure. A clean exit sends RESIGN: the RTI marks the federate NOT_CONNECTED, sets its NET to FOREVER — the strongest possible promise, “nothing further, ever” — gracefully shuts down the socket, and immediately re-runs the grant check on every downstream node, since that promise usually unblocks them at once. An unclean death (socket EOF, or FAILED) is handled similarly at the bookkeeping level, but the consequences differ by mode: in a federation whose remaining nodes depend on the deceased for absence information, the correct behavior is to stop the federation rather than let survivors advance on evidence that will never arrive. This asymmetry is worth internalizing — the RTI is a coordination authority, not a fault-tolerance layer, and centralized coordination makes every federate a potential single point of stall.

3.2 — Transient federates: joining a running federation

Recent versions relax the assumption that membership is fixed. A federate declared transient may connect to, and disconnect from, a federation already in progress — a diagnostic tool attaching to a running controller, a compute node elastically added. The hard question is which start tag a late-joining federate receives, because it must not be able to inject events into the past of nodes that have already advanced. The RTI computes an effective start tag as the maximum of five quantities: the tag the joiner proposes, the federation's original start tag, the joiner's own last completed tag plus a microstep (if it ran before), every downstream federate's last granted (P)TAG plus a microstep, and the largest tag ever addressed to it by an upstream federate plus a microstep — addressed, not received, which matters below. Each term rules out one way of arriving in someone's past. Under decentralized coordination the calculation is different and more precarious — the joiner's proposal plus DELAY_START, which is safe only if that margin exceeds the usual latency, clock-error and execution budget minus the joiner's declared maxwait; otherwise a safe-to-process violation is possible at the seam. Meanwhile upstream federates receive DOWNSTREAM_CONNECTED / DOWNSTREAM_DISCONNECTED notifications, and the grant algebra learns to discount absent transients so their non-membership does not block anyone.

Transience bends the grant path itself. The effective start tag is computed from tags already granted, so every grant the RTI issues while a transient is away narrows the window in which that transient can still join: grant far into the logical future and a federate that connects a second later is admitted at a tag far ahead of the wall clock, having missed the interval it was supposed to observe. The RTI’s answer is a delayed grant. When a federate has at least one upstream transient currently absent, its TAG and PTAG are not written to the socket; they go into a priority queue keyed by tag, at most one entry per federate, which a dedicated thread drains as physical time reaches each tag. A later recomputation that lowers the pending grant overwrites the queued entry rather than adding a second one; an equal one only updates its provisional flag. The effect is that a federation with absent transients advances logical time at roughly the rate of physical time instead of running ahead of it — paying throughput for the ability to be joined. Federates with no upstream transients skip the queue entirely, so a conventional federation pays nothing for the mechanism.

The queue defers a grant; it does not commit to one. When an entry finally expires the RTI re-examines it rather than sending it blind, and there are two ways it dies instead. If every upstream transient has reconnected in the meantime, the entry is stale — it was computed under an absence that no longer holds — so it is discarded and the ordinary decision function runs again from current state, because a queued tag must never bypass an EIMT check. If a later grant has already overtaken it, it is redundant and is dropped. Only an entry that passes both tests is written to the socket.

A second accommodation concerns the data plane. The RTI records, per transient, the largest tag any message has ever been addressed to it (max_intended_tag), including messages it dropped because the federate was away — that record is the fifth term of the effective start tag, and it is kept precisely so a later rejoin cannot land in the past of traffic that was already sent. Messages arriving for a transient that is absent, or addressed to a tag earlier than its effective start tag, are drained from the socket and discarded with a warning; the connection is kept and the message is discarded.

§ 04 / the grant algebra

Centralized coordination

The rule a federate obeys: before processing the event at the head of its queue, tag t, it sends NET(t) and blocks until the RTI proves safety. The RTI's side is a purely reactive fixed-point computation over the federate dependency graph — every incoming NET, LTC, or routed message updates one node's state and re-runs the safety check wherever that update could unblock someone. Each part of that sentence is precise in its own way.

Reactive. The RTI keeps no agenda of its own. Its state is a short record per node — the next event, clamped by the in-transit queue (Section 4.11), the last completed tag, the last TAG and the last PTAG granted — and everything it does answers a message. A NET from f changes f’s next event and re-checks f and its transitive downstreams; an LTC changes f’s completion and re-checks its downstreams; a forwarded message may lower its destination’s next event; a RESIGN sets it to FOREVER. “Wherever that update could unblock someone” is exact: only nodes whose safety test reads the updated value can change their answer, and the min-delay matrix names them (Section 4.10). “Purely” holds for the steady state of a federation of persistent federates, the subject of this section. Startup and shutdown are timed protocols (Section 3.1), clock synchronization keeps its own schedule (Section 6), and grants withheld for an absent transient are released as physical time reaches them (Section 3.2).

Over the dependency graph. The RTI sees no reactors, ports or reactions — only federates, the connections between them and the least after delay on each, as NEIGHBOR_STRUCTURE delivered them (Section 7). Every rule in Sections 4.1–4.14 is a function of that weighted graph and the per-node records, which is why the same algebra serves enclaves inside one process and could be built in hardware (Section 9.9).

Two fixed points and a safe advance. The structure is a fixed point computed once: the min-delay matrix is the least solution of a path relaxation over the (min, ⊕) semiring, found by relaxing until nothing improves and recomputed only when the topology changes (Section 4.5)[39]. The question about one node is a fixed point evaluated in one step: the earliest incoming message tag is defined recursively over the graph, but with the closure in hand it is a single scan of one matrix column (Section 4.6)[36]. The run is where the phrase is loosest: it is a safe, monotone advance rather than the fixed point of one defined function (Section 15.3). Completions and grants only move forward — the guards on last_granted and last_provisionally_granted drop anything that is not an improvement — so each message can only move the grants forward, toward tags the evidence justifies, the conservative-simulation pattern of null messages and LBTS carried out centrally (Section 4.14)[24],[29]. The PTAG walk is the most literal instance, an iteration inside one cascade that stops when the guards do (Section 4.3). One input moves backward: a federate that receives an earlier message lowers its NET. Nothing already granted is taken back; a lower NET only limits how far later grants can go, which is why a message still in flight must count as a next event (Section 4.11).

What it does not compute. For a zero-delay cycle, the fixed point that decides the program’s behaviour — which ports are present at a tag, and with what values — is computed by the federates, exchanging messages and absence notices under a PTAG. The RTI’s part concerns time only: how far each node may safely advance. Grant computation depends on tags, topology and protocol state, not on the values of application payloads; the centralized RTI process nevertheless forwards payloads, as described in Section 4.12.

Two elements of that listing are essential. scheduling_node_t is the first member of federate_info_t, so a pointer to one is a pointer to the other — that single-inheritance-by-layout technique is what lets the algebra in rti_common.c be literally the same code for federates and for enclaves (Section 4.8), with the transport-specific notify_* functions provided separately by each. And every tag field starts at NEVER, which is why “silence” needs an explicit rule: an upstream that has never sent a NET would otherwise look like an upstream that promised the beginning of time. The EIMT code handles it by writing the federation start tag into that node’s next_event the first time it is consulted — the conservative assumption is not only made but also recorded.

4.2 — The two safety conditions

Low-cost condition — upstream completion. Compute the minimum over immediate upstreams of completed pushed through the connection's after delay (lf_delay_strict). If that clears the federate's NET, grant — and grant that whole bound, not merely the NET: the RTI is maximal, answering with the furthest tag it can prove rather than the least it was asked, sparing future round-trips.

Expensive condition — earliest incoming message tag (EIMT). Otherwise compute, over all transitive upstreams, the minimum of (that node's NET + minimum path delay to here). The real implementation does not run a graph search per query: it lazily builds an all-pairs minimum-delay matrix min_delays[n×n] with a sparse relaxation (the source comments: “This is not Dijkstra's algorithm… There must be a name for this algorithm”), caches it until topology changes, and detects cycles during the build, setting per-node flags. Silence is conservative: an upstream never heard from is assumed able to send at the start tag.

4.3 — Why PTAG exists, and why it is contagious

A cycle of federates whose connections carry no delay is legal as long as the program is constructive: no reaction on the cycle may depend, at the same tag, on its own output (Section 7 states the boundary precisely). Two cycle members can each hold an event at the same tag and each need the other's absence information first — a real deadlock if grants were all-or-nothing. The PTAG breaks it: advance your clock, run every reaction whose inputs at the tag are known, and exchange the resulting messages and port-absent notices — which is exactly what resolves the cycle — but do not complete the tag: a reaction that reads a still-unknown input waits, and no LTC is sent until every input at the tag is resolved. The RTI then propagates the PTAG upstream — the source comment states the purpose plainly: “to stimulate absent messages from upstream and break deadlocks” — releasing the whole cycle at once. Each step visits every connected immediate upstream, not only those on zero-delay connections, and decides for it with the same tag g: a full TAG of g if that upstream's own EIMT exceeds g, a PTAG of g if its EIMT equals g and its strict EIMT exceeds g, nothing otherwise. Only an upstream that receives a PTAG carries the walk further, and guards on last_granted / last_provisionally_granted terminate the recursion. Honoring that restriction is the federate's job (Section 8); the protocol is cooperative, one reason optional federate authentication by keyed-hash message authentication code (HMAC) exists.

4.4 — The grant algebra: tag arithmetic itself

“Algebra” is meant literally: the RTI's decisions are min/max/compare operations over tags (t, m), closed under two addition-like operators whose quirks encode the semantics of connections. lf_delay_tag(g, d) answers “what tag does an event acquire crossing a connection with delay d?” — and the case analysis is the semantics: a negative interval encodes “no after clause at all” and leaves the tag untouched; an interval of exactly zero (after 0) increments the microstep; a positive interval adds to the time and resets the microstep to zero: the reset is part of the tag addition for a positive logical-time delay, and does not depend on how much physical time elapses. Two further operations must be kept apart. The predecessor of a finite tag, lf_tag_latest_earlier, is the largest tag strictly earlier: (t, m − 1) when m > 0, and (t − 1 ns, UINT_MAX) when m = 0 (the microstep is an unsigned 32-bit counter); NEVER and FOREVER are returned unchanged. lf_delay_strict(g, d) first computes lf_delay_tag(g, d) and takes the predecessor of the result only when d is a positive interval (not 0, NEVER or FOREVER) and the result is finite: across a connection with no declared delay it returns g itself, and across after 0 it returns (t, m + 1). The RTI uses it when a completion must bound what can arrive before a tag rather than at it (Section 4.9). Two consequences ripple through everything: sentinel values carry meaning (NEVER doubles as “no connection/no information,” FOREVER as “never,” and in the min-delay matrix “no delay” is the tag (0,0) while after 0 is (0,1)); and the operation is non-commutative — the source warns that a path delay must be computed as connection_delay + path_so_far and not the reverse, since adding a positive time first would wrongly erase microsteps the rest of the path preserves.

4.5 — The min-delay matrix

update_min_delays() lazily builds an n×n matrix of tags, min_delays[i·n + j] = the least total delay along any path of connections from node i to node j, with FOREVER meaning “i is not upstream of j at all.” The build is a per-node recursive relaxation walking upstream from each end node, accumulating path delays and recursing only when a path improves — which is also the termination argument, since path delays only decrease and are bounded below:

_update_min_delays_upstream(end, intermediate, path_delays[]):
  for each immediate upstream u of intermediate:
    path = delay(u → intermediate) + path_so_far     // order matters (Section 4.4)
    if path < path_delays[u]:
      path_delays[u] = path
      if u == end:                                  // relaxation returned home:
        end.flags |= IS_IN_CYCLE                    //   a cycle through end
        if path == (0,0) and last hop had no declared delay:
          end.flags |= IS_IN_ZERO_DELAY_CYCLE
      else:
        recurse(end, u, path_delays)                // keep relaxing upstream

Cycle detection is a side effect of the relaxation returning to its starting node, and the two flags it sets are consumed by the PTAG rule below. The authors note it is “not Dijkstra's algorithm” but one tuned for sparse upstream sets (“there must be a name for this algorithm”). The matrix is cached and recomputed only when topology changes — a federate joining or resigning — so the steady-state cost of every safety question below is a linear scan, not a graph search.

4.6 — EIMT, and its strict variant

The earliest incoming message tag for node e answers: over every transitive upstream i (every row of the matrix with a finite entry into e), what is the minimum of i's reported NET pushed through the minimum path delay? Silence is handled conservatively — an upstream never heard from is assumed able to send at the start tag — and the push uses plain lf_tag_add, so a positive-time path correctly forgets the upstream's microstep:

EIMT(e)        = min over transitive upstreams i of
                   ( NET(i) ⊕ min_delays[i][e] )        // ⊕ = lf_tag_add

EIMT_strict(e) = min over IMMEDIATE upstreams u NOT in a zero-delay cycle of
                   ( min( NET(u), EIMT(u) ) ⊕ delay(u → e) )

The strict variant differs in two deliberate ways: it consults only immediate upstreams and skips any that belong to a zero-delay cycle, and for each survivor it takes the earlier of that node's own next event and what could be relayed through it. It therefore measures the earliest threat from outside the cycle. That is exactly what the grant decision of Figure 7 needs: EIMT == NET with EIMT_strict > NET means the tie at the requested tag is manufactured by the node's own cycle — safe to release provisionally — whereas a tied EIMT_strict means a genuine external threat, and the node must wait.

  2. Read the column for A. The min-delay matrix already holds the least delay of each of those paths, computed once when the topology was built: (0,0) from S, A and B, FOREVER from C.
  3. Push each NET through its delay. S gives (50,0); A and B give (20,0). The minimum, (20,0), equals NET(A): a tie — something might still reach A at 20, so no TAG. That minimum is A’s own promise, relayed around the cycle.
  4. Strict EIMT. Of A’s immediate upstreams, B is in the zero-delay cycle and is skipped; S gives min(NET(S), EIMT(S)) = (50,0), above (20,0). The only outside threat comes later, so the tie is the cycle’s own: PTAG(20,0).

4.7 — The DNET candidate: tag subtraction

DNET runs the algebra in reverse. When node s reports a new NET, the RTI recomputes, for each node u upstream of s, “what is the earliest tag at which anything u could send would still matter to anyone downstream?” — the minimum over u's downstreams w of get_dnet_candidate(NET(w), min_delays[u][w]), a carefully cased tag subtraction A − B: if A < B the answer is NEVER (nothing u sends can matter yet); a microstep borrow decrements the time and saturates the microstep at UINT_MAX; and whenever the delay has a positive time part the microstep saturates too, the mirror image of addition having erased it. Two guards complete the picture: nodes in a zero-delay cycle are never sent DNETs (they are governed by the PTAG machinery instead), and a notification goes out only when the value changes. The payoff is pure traffic suppression: an upstream federate holding a DNET of X sends a NET for tag g only if g is strictly greater than X (federate.c adds a second condition, on the last NET actually sent), and a NET it suppresses is sent after all if a later DNET falls below it, sparing the RTI exactly the NET→recheck fan-out identified as the bottleneck in the note below. The paper that introduced it[23] reports the effect where it is designed to take effect: on a deliberately sparse workload — a fast timer, a rare event — the number of next-event signals falls from 100,161 to 677, and the authors quantify the gain as up to 148×, growing with sparsity.

4.8 — The same algebra inside one program: enclaves

Everything in this section has a second life that never touches a network. An enclave is a reactor subtree given its own scheduler and its own logical timeline within a single process — useful when one part of a program should run ahead or lag behind another (a slow planner beside a fast control loop) without splitting the program into separate executables. Enclaves coordinate through exactly the machinery of Sections 4.1–4.7: the file is named rti_common.c precisely because it is shared, its central type is scheduling_node_t rather than “federate,” and its log messages read “fed/encl” throughout. The difference is the transport — function calls and condition variables instead of sockets — and one simplification: zero-delay cycles are prohibited between enclaves, so the PTAG propagation of Section 4 is not needed there, as the source comments note. This is the first appearance of this document's central claim, and the simplest one to verify: the coordination contract is independent of the transport that carries it.

4.9 — The decision function, verbatim in structure

Everything so far assembles into one function, tag_advance_grant_if_safe(), which returns a small struct — a tag plus an is_provisional flag, with NEVER meaning “grant nothing.” Reading it in order exposes several branches the prose summary glosses over:

tag_advance_grant_if_safe(e) → {tag, is_provisional}:

  # ---- Phase 1: low-cost test over IMMEDIATE upstreams, using LTCs ----
  M = FOREVER; connected = 0
  for u in e.immediate_upstreams:
      if u.state == NOT_CONNECTED: continue        # resigned nodes are invisible
      connected += 1
      M = min(M, lf_delay_strict(u.completed, delay(u,e)))

  if connected == 0:                               # every upstream has gone away
      if no transients in federation: return FOREVER      # nothing can ever arrive again
      else: return max(e.next_event, max_stop_tag)        # a transient might rejoin
  elif M > e.last_granted and M >= e.next_event:
      return M                                     # maximal grant, no EIMT needed

  # ---- Phase 2: EIMT over TRANSITIVE upstreams, using NETs ----
  t_d = EIMT(e)                                    # Section 4.6, via the min-delay matrix
  for u in e.immediate_upstreams:                  # tightening pass
      t_d = min(t_d, lf_delay_tag(min(u.next_event, EIMT(u)), delay(u,e)))
  t_d_strict = EIMT_strict(e)                      # ignores zero-delay-cycle members

  # ---- Phase 3: the trichotomy ----
  if t_d > e.next_event > NEVER
     and t_d >= e.last_provisionally_granted       # note >=, not >
     and t_d >  e.last_granted:
      return lf_tag_latest_earlier(t_d)            # TAG: the largest tag strictly below t_d

  if t_d == e.next_event and is_in_zero_delay_cycle(e)
     and t_d_strict > e.next_event
     and t_d > e.last_provisionally_granted and t_d > e.last_granted:
      return {e.next_event, provisional: true}     # PTAG: exactly the requested tag

  return NEVER                                     # wait

Five details reward attention.

The two phases use different evidence. Phase 1 reasons from completions (LTCs) over immediate neighbors only — inexpensive and strong, because a completed tag is a fact about the past. Phase 2 reasons from intentions (NETs) over the transitive closure — expensive, and weaker, because a NET is a revisable promise. The function always tries the low-cost evidence first, and note it uses lf_delay_strict there (Section 4.4): from “u finished tag g” across a positive delay d the RTI may conclude only that nothing arrives strictly before g ⊕ d, hence the step back to the predecessor; across a connection with no declared delay or with after 0, the bound is g itself or g plus one microstep, with no step back.

Disconnection is a grant condition. If every immediate upstream has resigned, nothing can ever arrive again and the node is granted FOREVER outright so it can run to completion and exit. That branch is subtle in the presence of transients: a disconnected upstream might rejoin, so the RTI must not grant FOREVER; it grants the node's own next event instead, safe because a rejoining transient is admitted at an effective start tag strictly greater than anything already granted here (Section 3.2).

The DNET optimization can poison this path. The comments record a real bug and its fix: because DNET (Section 4.7) lets a federate suppress every NET at or below its DNET threshold, a node's recorded next_event can be stale — behind last_granted. During shutdown, granting that stale value produces a redundant grant, which the guards suppress, and the federation stalls one microstep short of the stop tag. Hence the clamp to max_stop_tag. This is the recurring hazard of caching in a protocol whose correctness is defined over the freshest information: every suppression optimization must be re-examined against every termination path.

The tightening loop guards against over-granting. After computing EIMT from the matrix, the function makes a second pass over immediate upstreams taking min(u.next_event, EIMT(u)). The reason, per the source comment: an intermediate node whose own NET is FOREVER (it has no local events) may still relay messages from further upstream, and the purely transitive walk can miss that once connectivity changes. It is a belt-and-braces bound — the same quantity eimt_strict computes, but without excluding cycle members.

The redundancy guards are asymmetric, deliberately. For a TAG the test against last_provisionally_granted is >=, not > — the comment says equality “is important to override any previous PTAGs.” A federate sitting at a tag under a provisional grant is waiting for exactly that confirmation; refusing to re-send at the same tag because “we already granted it” would strand it forever. For a PTAG both tests are strict, since re-issuing an identical provisional grant conveys nothing new. And note what each branch returns: lf_tag_latest_earlier(t_d) for TAG — the maximum provably safe tag, often far beyond what was asked — versus exactly e.next_event for PTAG, because a provisional release is only ever justified for the specific tied tag.

4.10 — Fan-out, locking, and cost

The decision function is pure computation; the surrounding layer decides when to run it and whom to notify. notify_advance_grant_if_safe(e) calls it and dispatches to the TAG or PTAG sender if the result is not NEVER, so no caller ever inspects the struct directly. The interesting one is update_scheduling_node_next_event_tag_locked(e, net), which runs on every NET arrival and performs four steps in a fixed order:

e.next_event = net
if e has upstreams:  notify_advance_grant_if_safe(e)      # 1. maybe grant e itself
else:                e.last_granted = net                 #    sources self-grant
update_min_delays()                                       # 2. refresh matrix if stale
for j where min_delays[e][j] != FOREVER:                  # 3. every DOWNSTREAM node
    notify_advance_grant_if_safe(scheduling_nodes[j])
if DNET enabled:
    for i where min_delays[i][e] != FOREVER, i != e:      # 4. every UPSTREAM node
        d = downstream_next_event_tag(i, e.id)
        if d != i.last_DNET and i.next_event <= d: notify_downstream_next_event_tag(i, d)

Note that steps 3 and 4 traverse the transitive sets, read straight off the rows and columns of the min-delay matrix — one row scan for downstreams, one column scan for upstreams. A node with no upstreams is a source and grants itself: it never waits, and the RTI merely records the fact so downstream reasoning stays uniform. The visited array is worth locating precisely, because it is readily attributed to the wrong walk: it belongs to the downstream notification that follows an LTC, which recurses through immediate_downstreams and allocates a per-call boolean array to avoid revisiting a node in a cycle. The upstream PTAG propagation of Section 4.3 has no visited set at all — it terminates on the redundancy guards instead, since a node that has already been granted that tag or later returns immediately. Two recursive walks over the same cyclic graph, two different termination arguments.

Concurrency. The RTI is one thread per federate socket over shared state, so nearly every function in this section carries the contract “assumes the caller holds the RTI mutex” — visible in the _locked suffix on the entry point above. The listener thread that parsed a NET takes the mutex, runs the whole cascade (possibly writing grants to several other federates' sockets), and releases it. One coarse lock for the entire grant computation is the deliberate choice: the decision reads the state of arbitrarily many nodes, so anything finer would need a lock order over the dependency graph — which, given cycles, is exactly the problem the protocol exists to solve.

Where the time goes. Let n be the number of nodes, d the average in-degree. Phase 1 is O(d). Phase 2 is O(n) per EIMT scan, but the tightening loop calls EIMT once per immediate upstream, making a single decision O(n·d) in the worst case. Each NET then triggers that decision once per transitive downstream, plus a DNET computation per transitive upstream. The matrix build itself is the sparse relaxation of Section 4.5, amortized to zero in steady state because it is cached until membership changes. So the dominant term is the fan-out, not the path math — concretely O(n·(n·d)) worst case per NET in a densely connected federation. That product is an asymptotic characterization of the coordination cost behind the “broker becomes a bottleneck” critique below, and it is exactly what DNET attacks: not by reducing the cost of any decision, but by eliminating the NETs that trigger them.

Cost model. As quantified in Section 4.10, the dominant cost is the notification fan-out per NET, not the path math (which is cached). This is the concrete mechanism behind the classic criticism that an HLA-style broker becomes a bottleneck — and the concrete motivation for the coordination mode in the next section, which deletes this entire code path.

One asymmetry in that machinery repays attention, because it appears to be duplication and is not. An arriving NET reaches its transitive downstream set through the matrix: one row scan, every node with a finite entry, no recursion. An arriving LTC reaches the same set through the graph: it notifies immediate downstreams and then walks onward recursively, carrying a heap-allocated visited array so a cycle cannot send it round forever. Same destination set, two entirely different traversals, and the second one allocates on every LTC. The reason is historical rather than principled — the matrix postdates the graph walk — and it is a clear example of what a reimplementation may discard: in hardware both reduce to the same operation, one parallel evaluation of the decision function over all n nodes, where reaching a node twice adds no latency because nothing is sequential to begin with.

4.11 — In-transit messages: what the RTI knows that the federates do not

Under centralized coordination the RTI is both the referee and the postal service, and the second role gives it a fact the first role could not otherwise obtain: which messages it has already forwarded that the destination has not yet finished processing. A NET is a statement about a federate’s own event queue. It carries no information about a message in flight toward that federate, because the federate does not know about it yet.

So the RTI keeps one more structure per federate, a tag priority queue of in-transit messages. Each TAGGED_MESSAGE it forwards has its intended tag inserted — unless the destination has already completed that tag, the one case the queue cannot help with and which is treated below; every LTC removes all entries up to the completed tag. The queue enters the algebra at exactly one point, and it is the point where a federate’s NET is recorded:

update_federate_next_event_tag_locked(fed, net):
    net = min(net, earliest tag in fed.in_transit_message_tags)
    update_scheduling_node_next_event_tag_locked(&fed.enclave, net)   // Section 4.10

A federate that reports “my next event is at tag 10” while a message addressed to tag 4 is still crossing the wire is therefore recorded as having a next event at 4. Without that clamp the RTI could prove, from the federate’s own optimistic NET, that nothing early can reach its downstream neighbors — and grant them past a tag whose message is sitting in a socket buffer. The clamp is small, and it is the difference between a coordinator that reasons about the network it is running and one that reasons about the network it was told about.

The steps of Figure 12

  1. A message in flight. S sends A a message tagged 4. The RTI forwards it and inserts 4 into the in-transit queue it keeps for A; A has not received it yet.
  2. A reports NET(10). A, unaware of the message, truthfully reports its next event from its own queue: 10.
  3. The RTI clamps. The RTI records min(10, 4) = 4 as A’s next event, so C, 10 ms downstream of A through B, can be granted only up to the predecessor of (14 ms, 0), not 20 ms. The record covers the message still on the wire.
  4. LTC(4) clears the entry. The message lands; A handles tag 4 and sends LTC(4). Only then does the RTI drop every in-transit entry up to 4, and A’s next NET, 10, is recorded as it is.

What Figure 12 shows. A NET describes the federate’s queue; the RTI’s record also covers the network between them.

Two corollaries. First, forwarding a message whose tag is earlier than the destination’s recorded NET immediately triggers the full cascade for that destination — the RTI does not wait for the federate to notice the early arrival and retract its own NET (the red edge of the federate scheduler in Section 8). Second, if a message arrives for a tag the destination has already completed, the RTI cannot fix it; it logs an error naming the safe-to-process violation that is about to happen. In centralized mode that is a bug in the coordination, not a tolerated fault, and the error message states this explicitly.

This is the part of the RTI that a naive translation to hardware does not preserve. A design that keeps the data plane out of the coordinator — reactors wired directly to each other, the coordinator seeing only NET, TAG and LTC — has thrown away the state this subsection depends on, and has to recover the same information from the occupancy of the connection buffers themselves. That is precisely what Section 9.2’s “absence is a wire that is always driven” provides: when every connection carries a token at every tag, in-transit is not a separate fact to be remembered, it is the state of the wire.

4.12 — Threads, one lock, and what actually runs under it

The RTI is more concurrent than the algebra suggests. At steady state it runs one thread per federate TCP connection — the workhorse, created when the connection is accepted, which parses that federate’s messages and runs the whole cascade in response — plus a clock synchronization thread (Section 6), a thread that keeps listening for transient federates through the entire execution phase, the delayed-grants thread of Section 3.2, and a small thread that answers connections arriving after the federation is full so that an unexpected client receives a REJECT rather than a hang. Each stop request spawns one more, the timeout thread of Section 3.1.

All of them serialize on a single global mutex. The _locked suffix and the “assumes the caller holds the RTI mutex” contracts mark the functions that expect it already held, with one exception worth remembering when reading the code: the LTC entry point takes the lock itself. What runs inside the critical section is the whole of Section 4 — the decision function, the EIMT scans, a matrix rebuild if the topology changed, and the socket writes for every grant the cascade produces, to arbitrarily many federates.

The lock is also recursive, deliberately: the runtime initializes every mutex with PTHREAD_MUTEX_RECURSIVE, so a function reached from inside the critical section may take it again without deadlocking. That is what makes the failure path below legal, since it reacquires a lock its caller already holds. It is also a design choice for which the source explicitly documents a potential deadlock hazard: the comment beside it quotes the POSIX advice against combining a recursive mutex with condition variables — the implicit unlock inside a wait may not actually release a lock that was taken more than once, leaving no thread able to satisfy the predicate — and then questions whether the implementations have fixed it. The RTI waits on condition variables under this mutex in several places (Section 3.1). The hazard is latent rather than observed, but it should be known before a hang is attributed to a defect in one’s own program.

Less visibly, the mutex also covers the data plane. A forwarded message is copied through a buffer of 256 bytes with the global mutex held for the entire transfer: a one-megabyte payload is roughly four thousand read-then-write chunks, during every one of which no grant can be computed anywhere in the federation. The source carries a FIXME saying as much — that each outgoing connection should have its own mutex — and it is the direct answer to the question Section 4.10 raises about where a centralized coordinator actually becomes a bottleneck. It is not the path arithmetic, which is cached, and usually not even the notification fan-out. It is that coordination and bulk data share one lock.

Failure handling under that lock is deliberately soft. A write that fails does not abort the RTI and does not propagate an error upward; it marks that federate NOT_CONNECTED and, if it was a transient, notifies its peers. The next decision for any downstream node then finds one fewer connected upstream and takes the disconnection branch of Section 4.9 on its own. A federate dying mid-grant is not a special case in the protocol — it is an ordinary input to the same algebra, which is why that branch had to be written so carefully.

4.13 — The algebra on one federation, end to end

Every rule so far has been stated in isolation. This subsection runs all of them on one small federation, with real numbers, because several of the rules only make sense once you have seen them interact — in particular the fact that a node in a cycle is upstream of itself, which is where the PTAG rule comes from.

Four federates. A source S driven by a timer; A and B connected to each other in both directions with no after on either connection, which makes them a zero-delay cycle; and C, fed from B through after 10 msec:

  b.out    -> c.in after 10 msec;    //            → (10ms,0)

Moment one: the cycle blocks itself, and a PTAG releases it

Suppose the RTI currently holds NET(S) = (50, 0), NET(A) = NET(B) = NET(C) = (20, 0), and every node has completed (10, 0). A requests an advance to 20 ms. Phase 1 of Section 4.9 looks at A’s immediate upstreams, S and B, both of which have completed (10, 0) across connections with no declared delay; for such a connection lf_delay_strict returns the completion unchanged, so M is (10 ms, 0) — nowhere near the requested 20. The tie is manufactured by A’s own promise, relayed around the cycle at zero delay and arriving back at A as a threat to itself. Nothing outside the cycle can reach A before 50 ms. That is precisely the PTAG condition of Section 4.9: equality on EIMT, membership in a zero-delay cycle, and a strict variant that clears. A is granted a provisional advance to exactly (20, 0) — not to the largest provable tag, because a provisional release is only ever justified for the tied tag.

This is the maximal-grant rule of Section 4.2 in one line, and it is also where the microstep arithmetic shows itself: the 10 ms hop has a positive time part, so lf_tag_add discarded the upstream microsteps on the way through, and lf_tag_latest_earlier put a saturated microstep back at the boundary.

Moment three: DNET silences the source

Now give S a 1 ms timer while the rest of the federation works at 20 ms. Every tick would otherwise produce a NET, and every NET would re-run the cascade of Section 4.10 across the federation. The DNET computation of Section 4.7 runs the algebra backwards over S’s row:

DNET(S) = min over S's downstreams w of ( NET(w) ⊖ min_delays[S][w] )
        = min( A: (20,0) ⊖ (0,0)     = (20,0),
               B: (20,0) ⊖ (0,0)     = (20,0),
               C: (20,0) ⊖ (10ms,0)  = (10ms, UINT_MAX) )
        = (10ms, UINT_MAX)

The saturated microstep in the last term is the mirror of the addition that erased one: a positive time part in the delay means the microstep could not have survived the crossing, so the subtraction cannot recover it and saturates instead. S may now stay silent about every next event at or below that tag — the first ten ticks, not one NET among them — and speaks again the moment its next event passes it.

What makes the silence safe deserves stating plainly, because it is the opposite of what the word “optimization” usually implies. The RTI’s record of NET(S) goes stale, and a stale NET is an under-estimate: EIMT stays low, so grants are withheld that might have been issued. Suppression can only make the coordinator more conservative, never less — which is why it is safe, and also why the hazard of Section 4.9 exists at the one place where withholding a grant is fatal rather than merely slow: shutdown. And when S does finally send a message, the destination’s next event is lowered by the forwarding path itself (Section 4.11), not by a NET at all.

4.14 — Where the algebra comes from

Nothing in Sections 4.1–4.13 was invented from scratch for Lingua Franca. Each piece answers a question that distributed simulation, synchronous languages or graph algebra had already asked, and knowing the question explains why the answer has the shape it has — including the parts that look like accidents of implementation.

How to read Figure 17. Distributed simulation provided the protocol: null messages and lookahead, their centralized form in the HLA, and the proof that zero lookahead forces a provisional grant. The semantics of time provided the meaning: superdense tags, and fixed points that make zero-delay cycles well defined. Years are those of the works cited in Section 4.14.

Conservative synchronization and lookahead. Chandy and Misra, and independently Bryant, posed the problem in the late 1970s: logical processes exchange timestamped messages over fixed channels, and each may process an event at time t only once no channel can still deliver anything earlier[24],[25]. Their device is the null message: a message with no content whose timestamp is a promise — my clock plus my lookahead, the least delay I add to anything I send. The RTI keeps this structure and moves it. A NET is a null message addressed to the coordinator instead of to the neighbours; an after delay is the lookahead of one connection; the min-delay matrix of Section 4.5 composes lookahead along every path; PORT_ABSENT is the null message of the data plane. What centralization changes is propagation. In the distributed scheme a promise travels hop by hop, and a cycle whose lookahead sums to zero can pass null messages around without ever raising anyone's bound, or deadlock outright; Chandy and Misra's later answer was to let the deadlock happen, detect it and break it[26]. A coordinator that holds every promise computes the transitive bound in one step — EIMT — and needs neither. The other school, optimistic execution (Jefferson's Time Warp[27]), processes speculatively and rolls back when a straggler arrives; Fujimoto's survey remains the standard map of both[28]. Rollback is not available once an actuator has moved, which is why every Lingua Franca coordinator is conservative.

HLA time management: the same computation, named. The High Level Architecture turned conservative synchronization into a service interface, and it is where the RTI's vocabulary comes from[6],[29]. Its central quantity is the lower bound on time stamp, LBTS: for a federate F, “the minimum (current_timei + lookaheadi) computed over all other federates that send” time-stamp-ordered messages to F. EIMT is LBTS, taken over the transitive closure and in superdense time. An HLA federate requests an advance with Time Advance Request, or with Next Event Request — advance to t or to the next incoming message, whichever is earlier — and the RTI answers with a Time Advance Grant once it has delivered everything at or below the granted time. NET corresponds to Next Event Request and TAG keeps its name. IEEE 1516 renamed Next Event Request to Next Message Request, and the reference source still carries a FIXME proposing to merge LTC and NET into exactly that. Lingua Franca adds two elements: the grant is maximal, the latest tag below EIMT rather than the tag requested; and LTC gives the coordinator evidence about completed work that lets it skip the bound computation altogether (Section 4.2).

Zero lookahead, and why PTAG cannot be avoided. The first HLA specification required lookahead to be strictly positive, and Fujimoto then proved why it had to: “If zero lookahead is allowed, it is impossible for a Time Advance Grant to time T to guarantee it has delivered all messages with time stamp equal to T”[30] — the granted federate may itself send at T and provoke a reply at T. His remedy was a second, weaker family of requests, later standardized in IEEE 1516 as the “Available” variants (Time Advance Request Available, Next Message Request Available), whose grant promises only that every message strictly before T has been delivered, while more may still arrive at T. That is exactly the promise of a PTAG. The zero-delay cycles of Section 4.3 are zero lookahead, and the theorem shows that no refinement of the algebra can make a full grant safe there: the provisional grant is not a workaround but the strongest statement that is true. What Lingua Franca adds is when to fall back to it — only when strict EIMT shows the tie to be the node's own cycle (Section 4.6). The same paper observed that, for runs to be repeatable, events with equal time stamps must be ordered by the federates, not by the RTI. Lingua Franca settles that in the language instead: microsteps and declared reaction order make simultaneity deterministic before any coordinator is involved.

Superdense time and the word “tag”. The pair (t, m) is superdense time, introduced for hybrid systems by Maler, Manna and Pnueli so that a system can take several ordered steps at one instant[31]. The word tag comes from the tagged-signal model of Lee and Sangiovanni-Vincentelli, which describes every model of computation as sets of (tag, value) events over an ordered tag set[32]. The microstep reset of Section 4.4 is superdense time's defining asymmetry, and the non-commutativity the source warns about follows from it.

Fixed points: what a zero-delay cycle means. Inside one tag, a zero-delay cycle is a synchronous feedback system, and its meaning is the least fixed point of its components viewed as monotone functions over the order “unknown” below “present” and “absent”[33]. A program is constructive, in Berry's sense, when iterating from “everything unknown” resolves every signal[34]; Lingua Franca rejects programs whose cycles are not. Across tags, the Banach fixed-point theorem gives a network in which every cycle carries a delay exactly one behaviour, computable by iteration, and Cataldo et al. extended that result to superdense time[35]. The two results divide the work visible in Section 4.3. A delay around a cycle is what lets EIMT settle a tag in advance; where the delay is zero, the fixed point has to be computed inside the tag, by the federates themselves, and a PTAG is the permission to start: advance, exchange presence and absence, and complete the tag only once every input is known. Donovan et al. formalize the coordination along these lines and show that the real requirement for distributed execution is constructiveness, not a delay on every cycle. Their EIMT for node i is Bi = minj(min(Nj, H(Qj)) + Dij), in which the head of the queue of messages in transit to j, H(Qj), appears beside j's NET — the clamp of Section 4.11 is part of the definition, not a patch[36].

The matrix is a semiring closure. Least delays over all paths are an instance of the algebraic path problem: the closure of a matrix over a semiring whose “addition” is min and whose “multiplication” is delay composition. The classical algorithms — Floyd–Warshall, and its systolic-array form[39] — need composition to be associative and to distribute over min, which monotonicity provides. They do not need it to be commutative. That is why the non-commutative tag addition of Section 4.4 does not break the closure, provided every product keeps path order.

Not Lamport clocks. Lamport's logical clocks[40] order events after the fact, consistently with the messages that were actually sent. Lingua Franca tags run the other way: the program assigns them before anything is sent, and the RTI's job is to make execution respect an order that already exists. That is why a coordinator must be able to make a component wait, and a Lamport clock never does.

What the theory states about the cost. The CAL theorem of Lee et al. generalizes Brewer's CAP: as latency L between components grows, inconsistency and unavailability cannot both stay bounded, and the relation among the three is linear in max-plus algebra[37]. Centralized coordination is the fully consistent corner — every advance waits for a proof, so latency is paid entirely as unavailability. Decentralized coordination (Section 5) obtains availability through a safe-to-advance offset and becomes inconsistent when the offset is exceeded. And the same algebra governs enclaves inside one process (Section 4.8), where the timelines are separate but the transport is a function call[38].

§ 05 / clocks over grants

Decentralized coordination

Set coordination: decentralized and the entire grant apparatus compiles away. Federates open direct sockets to their peers — but the RTI is still the introducer: each federate advertises its listening port with ADDRESS_ADVERTISEMENT and resolves a peer with ADDRESS_QUERY before connecting, so the mode is peer-to-peer in its data plane, not in its bootstrap. Past that point the RTI keeps only startup, clock sync, and shutdown. The lineage is Ptides[7] and, independently, Google Spanner[8]: replace communication about safety with assumptions about time. Ptides deserves more than a name-drop — it is where most of this mode's ideas were invented — so after the mechanics, Section 5.1 examines it properly.

Each federate self-grants: it may advance to tag t once its physical clock reads t + STA, where STA (“safe to advance”) is a per-federate offset. In current Lingua Franca it is written @maxwait(…) on the federate’s instantiation, and per connection @absent_after(…); its default is forever, so a decentralized federate that is given no bound waits for every input to become known before it advances. Older material — and parts of the LF codebase — call this the STP offset, from “safe to process”; Section 5.2 explains why the notion was split in two, and this document uses STA for the federate-level offset and STAA for its per-port refinement throughout. The offline safety argument, per inbound connection:

after > E + L + D

— the after delay must exceed clock-synchronization error E, plus a bound L on network latency, plus the sender's lag D (physical send time minus the message's timestamp, enforceable with a deadline on the sending reaction). If it holds, any real message physically arrives before the receiver's clock reaches the message's own tag, so waiting until the tag suffices; the after creates the flight window. Feedback cycles need no special treatment — every edge already carries delay for the STA math.

The new failure mode. If the assumptions break — a latency spike past L — a message can arrive for a tag the receiver already advanced past. Determinism is violated detectably: the runtime invokes the reaction's STAA violation handler (“safe to assume absent”; written tardy {=…=} after the reaction body in current Lingua Franca, STAA(…) {=…=} in older versions), an alternate body that decides — process late, drop, log, degrade. Centralized mode has a liveness failure (everything stalls on a slow party); decentralized converts it to a bounded, handled fault. For control systems that would rather act on one stale packet than freeze, that is often the right trade.

Tuning is one budget spent in two places: larger after delays add pipeline latency but keep STA at zero; a nonzero STA adds physical lag at the receiver but tolerates smaller delays. Both purchase headroom against E + L + D.

5.1 — Ptides in detail: the intellectual ancestor

Ptides (Programming Temporally Integrated Distributed Embedded Systems, also written PTIDES in the literature and in the titles cited here; Zhao, Lee, and Liu, RTAS 2007[7], developed at Berkeley through roughly 2012 with John Eidson, an architect of IEEE 1588) began from a provocation: discrete-event (DE) semantics — timestamped events processed in timestamp order — had long been a simulation technology; Ptides proposed it as an executable specification for real distributed real-time systems. The obstacle was known from decades of distributed simulation. Conservative execution (Chandy–Misra–Bryant[24],[25]) lets a node process timestamp t only after every upstream neighbor promises nothing earlier, which requires constant “null message” traffic — the ancestor of the RTI's PORT_ABSENT and grant machinery of Section 4. Optimistic execution (Time Warp[27]) speculates and rolls back on late arrivals — unusable once you have actuated the physical world. Ptides contributed a third source of certainty: synchronized physical clocks. Its execution strategy[19] is explicit about the move: use clock synchronization as a replacement for null-message communication, and allow causally independent events to be processed out of timestamp order while the analysis guarantees dependent ones are not.

The three bindings. Ptides relates model time to physical time only at the system's edges, more surgically than a blanket “logical time chases the wall clock”: (1) at sensors, an event is stamped with the physical time of the occurrence it measures, making every timestamp in the system a faithful measurement; (2) at actuators, the timestamp is a deadline — an event with timestamp τ must arrive before physical time reaches τ, and the actuator may then release its effect exactly at τ, turning end-to-end latency into a semantic property rather than a performance accident; (3) at network interfaces, an event with timestamp τ must be handed to the network before physical time exceeds τ, and network delay is assumed bounded. Everywhere between the edges, model time and physical time are decoupled — a platform may lag behind or race ahead internally, which is precisely the slack a scheduler needs.

Safe-to-process analysis. From those bindings plus a clock-error bound e and a network-delay bound d, a static analysis derives, per input port, an offset δ such that an event with timestamp τ may be processed once the local clock reads τ + δ, with any later-arriving lower-timestamp message a locally detectable fault rather than a silent corruption. That sentence already contains all of Section 5: LF's after > E + L + D is the same inequality with renamed variables, the per-port STAA offsets are δ, and the STAA violation handler is the fault path. Google's Spanner[8] arrived at the same structure independently in 2012 — TrueTime's uncertainty interval plus commit-wait is “wait out the clock error before declaring an order” for database external consistency — which the Ptides lineage reasonably cites as convergent validation from an entirely different industry.

It was built, not only published. The Ptolemy II PtidesDirector co-simulated plant dynamics, platform delays, and networks against the same model; a code generator then targeted PtidyOS[20], a threadless, single-stack microkernel in which event processing runs inside reentrant interrupt service routines, scheduling is earliest-deadline-first over deadlines derived from timestamps, and there is no dynamic allocation — on ARM Cortex-M and XMOS boards with IEEE 1588 hardware timestamping, demonstrated on smart-grid protection applications[21]. Hold PtidyOS next to Section 10 and the family resemblance is striking: the threadless event-driven kernel and the deadline-as-semantics discipline are the software anticipation of what FlexPRET later did in silicon — unsurprisingly, since PRET and Ptides ran as companion projects in the same group.

Decentralized LF builds on Ptides’ physical-time semantics and makes the trade-offs among coordination offsets, consistency, availability and latency explicit[22],[37].

5.3 — micro-LF: decentralized coordination without an RTI

What micro-LF is. micro-LF is the implementation of Lingua Franca for microcontrollers and other resource-constrained systems: programs are compiled to C by its own compiler, ulfc, and run on the reactor-uc runtime[48],[49]. The runtime performs no dynamic memory allocation once the program runs: event queues, payload buffers and network buffers are allocated with sizes fixed at compile time. It targets POSIX hosts, the Zephyr, RIOT and FreeRTOS operating systems, the Raspberry Pi Pico SDK and ESP-IDF, and the Patmos and FlexPRET processors[48],[49],[50]. Its federated execution differs from the decentralized mode of reactor-c (Section 5) in one structural respect: the runtime contains no RTI. Every coordination message — tagged data, startup and shutdown coordination, clock synchronization — is exchanged between neighbors, federates joined by at least one connection, over the network channels declared in the program: TCP, UART, CoAP, Bluetooth LE, the S4NOC of Section 10.2 on Patmos, or a channel supplied by the user[48],[49]. The account below distinguishes three kinds of statement. Statements about the implementation describe reactor-uc at commit df7cfea (7 September 2026) and the micro-LF documentation consulted on 7 October 2026; historical design rationale is attributed to its source; and paragraphs marked as interpretation are this document’s reading, not claims of either source.

Peer-to-peer, stated precisely. In the decentralized mode of reactor-c the data plane is peer-to-peer, but the RTI still introduces federates to one another and keeps startup, clock synchronization and shutdown (opening of Section 5); earlier work on running that mode on embedded boards retained the same division[51]. In reactor-uc none of these functions is centralized, and they are not all symmetric either[49]. Startup: each federate exchanges a handshake with its neighbors and then runs a fixed number of rounds of start-time proposals, keeping the largest value received; the number of rounds is the longest-path length that the compiler computes for the undirected graph of neighbors, by two breadth-first sweeps. With clock synchronization enabled, only the clock-synchronization grandmaster proposes a time (its clock plus 100 ms per round) and the other federates propose NEVER, so the agreed start time is the grandmaster’s proposal; a federate joining a running federation requests the start time from its neighbors instead. Clock synchronization: one federate is designated grandmaster with @clock_sync(grandmaster=true); every other federate synchronizes with the neighbor closest to the grandmaster, by a four-timestamp exchange in the style of IEEE 1588 and a proportional–integral servo whose default gains are taken from linuxptp[48],[49]. Shutdown: an announcement carrying the shutdown tag is forwarded from neighbor to neighbor with a step count. The architectural distinction is therefore narrower than “there is no central node”: the grandmaster is a distinguished node, but no central process takes part in the ordinary advance of logical time. Decentralized reactor-c shares that property; reactor-uc extends it to startup and clock synchronization. (Interpretation: the two-sweep computation of the round count is exact when the graph of neighbors is a tree; this document has not examined whether it reaches the diameter of every cyclic topology, which a maximum computed by flooding requires.)

The question, and two ways to answer it. A federate about to process tag g = (t, m) faces the question of Section 4 and of the opening of Section 5: can a message with a tag at or before g still arrive on one of its inputs? An input is resolved at g when that possibility is excluded. Centralized coordination answers with logical evidence held by a third party: the RTI combines the topology (the min-delay matrix of Section 4.5) with every federate’s promises and completions (NET, LTC) and the messages in transit (Section 4.11), and it issues a TAG or PTAG only when that evidence excludes an earlier message; the HW-RTI of Section 9.9 implements the same decision in hardware. Decentralized coordination answers locally: the federate combines what it has received on each input with a waiting bound written into the program and its physical clock (Figure 19).

What the runtime records: TaggedMessage and last_known_tag. A value sent across a federated connection travels as a TaggedMessage: the sender’s current tag (time and microstep), a connection identifier and the serialized payload, at most 832 bytes in the current message definition; one network channel carries every connection between two neighbors[48],[49]. The sender transmits at most one message per connection and tag, at the tag at which the output was set, so on one connection tags arrive in increasing order provided the channel preserves order. On reception the runtime applies the connection’s after delay (on a physical connection it uses the receiver’s physical time as the base instead), schedules the event, and raises last_known_tag to the resulting tag. The field belongs to the runtime’s FederatedInputConnection, one per incoming federated connection, not to the input port, and it starts at NEVER[49].

Why the last received tag is not enough. If last_known_tag ≥ g the input is resolved at g: the message at g, if there is one, has arrived, and an order-preserving channel cannot deliver an earlier one afterwards. The converse fails. last_known_tag advances when a tagged message arrives, and otherwise only when a neighbor that joins a running federation announces its joining time; the protocol has no message that reports absence tag by tag: FederateMessage carries tagged data and startup, shutdown and clock-synchronization traffic, but no counterpart of reactor-c’s PORT_ABSENT or of a NET[49]. An upstream federate that has nothing to send at g leaves last_known_tag below g, and the receiver cannot distinguish that silence from a message still in transit or from an upstream federate that has not yet reached g. The field also says nothing about the federate’s other inputs, and its ordering inference rests on in-order delivery, which a channel that loses or reorders messages does not provide. Whatever the last received tag, absence at g has to be established by other means.

Absence as a timing decision: @maxwait. Before committing to g, and after its clock has reached t, the runtime examines every input whose channel is connected. If some have last_known_tag < g, it waits until its physical clock — the synchronized one when clock synchronization is enabled — reads t + W, W being the largest waiting bound among those inputs, and then commits to g[48],[49]. A message that arrives during the wait interrupts it, and the scheduler repeats the decision from the beginning, possibly for an earlier tag; t + W is an absolute deadline, so repetitions do not extend it. The bound is written @maxwait(…), on a connection or on the instantiation of the destination federate, the connection’s value taking precedence; 0 means no waiting, and the default is forever, under which a federate does not advance while any connected input is unresolved. Absence is thus established in three ways at the examined commit: by a later-tagged message on the same connection; by the passage of physical time; and, for a neighbor that joins a running federation, by the joining time it announces, which the runtime writes into last_known_tag of the inputs from that neighbor, so that no message is awaited from it before that time. As written at that commit, the loop that performs this write indexes the inputs with the loop variable of the bundles rather than that of the inputs, writes without the connection’s lock and can lower the field; it appears to be a defect, not yet confirmed upstream, and the behaviour described here is the evident intent[49]. In reactor-c the same role is played by @maxwait on the instantiation and @absent_after on a connection (opening of Section 5); the micro-LF compiler at the examined commit defines @maxwait for both positions and no @absent_after. The names STA (“safe to advance”), STAA (“safe to assume absent”) and STP (“safe to process”) used earlier in Section 5 and in older literature are historical terminology; reactor-uc retains STP only in identifiers and log messages.

Logical and physical time. The rule relates the two times at one point: a tag with time t is committed when the physical clock reads t + W. Whether that is safe depends on quantities that the runtime neither measures nor checks: the residual clock-synchronization error between sender and receiver, the transmission delay, the lag between the sender’s physical time and the tags at which it sends, and the connection’s after delay. reactor-uc derives no bound from them; W is the programmer’s choice. (Interpretation, not computed by the runtime: with E, L and D bounded as in the opening of Section 5, a message tagged τ is sent by physical time τ + D and received, as read on the receiver’s clock, by τ + D + L + E, while the receiver waits until τ + after + W. The condition after + W > E + L + D is therefore sufficient, and W = 0 gives back the inequality of Section 5.)

When the assumption fails. A message whose tag is at or before the federate’s current tag cannot be scheduled. The runtime then logs a safe-to-process violation and schedules the event at the current time with the microstep increased by one, keeping the original tag as the event’s intended tag[49]. At that later tag, a reaction that the port triggers, or that reads it, runs its tardy handler instead of its body when the port’s value carries a different intended tag; a reaction without a handler runs its body on the late value at the later tag, and the runtime logs a warning. Preallocation imposes further bounds: when the payload buffer of a connection is full, the incoming message is dropped, an error is logged and last_known_tag is left unchanged; when the message cannot be deserialized, or the event queue is full, the event is dropped as well, but last_known_tag still advances to its tag, so the input counts as resolved at that tag although its value was lost. The violation is therefore detected, and the program determines its consequence; it is not prevented. Centralized coordination aims at prevention: no grant is issued while the logical evidence leaves room for an earlier message, so its failure mode is waiting, a loss of liveness, rather than a late value. Both rest on assumptions — centralized coordination on reliable delivery and on federates that keep their promises, decentralized coordination in addition on its timing bounds — and they do not provide identical guarantees. Semantic determinism, in the sense of Section 1.1, holds for a micro-LF federation as long as the timing bounds hold and the inputs, including physical actions, are the same; the documentation’s statement that federated programs keep their determinism guarantees[48] should be read with that condition.

§ 06 / the E bound

Clock synchronization

Because the entire decentralized argument depends on E, LF ships its own software clock sync[4] (disable it if the network has PTP — the Precision Time Protocol, IEEE 1588). The RTI's host clock is master; each remote federate runs the classic four-timestamp exchange over a dedicated UDP channel (TCP's queuing would poison the measurements): master sends at T1, slave stamps receipt T2, replies at T3, master stamps T4 and returns it. Offset = ((T2−T1)+(T3−T4))/2, exact when the path is symmetric — path asymmetry is the irreducible residual inside E.

Implementation choices worth knowing: the OS clock is never touched and never stepped — the runtime keeps a software offset added by lf_time_physical(), since a backward step would break the monotonic-logical-time invariant. In the steady state each round's correction is divided by an attenuation factor (default 10), a simple low-pass filter, so that the estimated offset converges instead of following jitter — but only there: during the startup exchange, which runs over TCP, the offset is set directly to the estimated error, there being no history yet to filter against. The UDP path adds a second, sharper filter: each exchange is followed by coded probes, a short burst whose spacing is known in advance, and a round whose probes arrive distorted is discarded outright rather than averaged in. Attenuation suppresses jitter; the probes reject the rounds that were measuring something other than the clock. Modes: off; init — the default — which runs the exchange only before the start tag (ten exchanges per interval); or on, which adds periodic rounds to track drift. The period of those rounds is a target option rather than a runtime constant, so read it out of your own configuration instead of assuming a figure. A test-offset option deliberately skews each federate's clock by (id+1)×offset to fault-inject the protocol. Same-host federates skip sync — detected by literal string comparison of the at clauses, so localhost vs 127.0.0.1 triggers pointless self-synchronization.

So what is E, numerically? The runtime publishes no figure, and a single number would be dishonest: E is dominated by path asymmetry and by whatever scheduler and queuing jitter remains after the attenuation and the coded probes — properties of your network and your load, not of LF. The orders of magnitude worth carrying as priors: hardware-timestamped PTP on a switched LAN reaches sub-microsecond; software timestamping on that same LAN lands in the tens to hundreds of microseconds; NTP across a WAN is milliseconds. LF’s own synchronization is software-timestamped over UDP, so it belongs in the middle band — and it should be measured rather than assumed, since the runtime collects clock-sync statistics (_LF_CLOCK_SYNC_COLLECT_STATS, on by default) and reports the observed offset and its spread per federate. These statistics characterize the observed variation of the offset estimate; they do not by themselves bound the estimation error, which also includes path asymmetry, drift between exchanges and conditions not present during the measurement. The E used in after > E + L + D therefore has to be a justified bound. An engineering estimate built from the measured spread, the known asymmetry of the path and an explicit margin is appropriate for design, provided it is identified as an estimate and not presented as a proven worst case. On one chip with one oscillator (Section 10), every node reads the same clock and E is zero by construction.

§ 07 / code generation

Compiling a federation

The compiler lfc performs surgery on the abstract syntax tree (AST). Each top-level instance becomes a standalone program; every boundary-crossing connection is deleted and replaced by a generated network sender in the source (serialize, prepend tag, write TAGGED_MESSAGE) and a network receiver action in the destination (the socket listener schedules it, injecting the event at the transmitted tag). To each federate's own scheduler, remote inputs are ordinary actions — all distribution is confined to shims.

The compiler performs three further analyses at the same time. Minimum-delay computation: for each federate pair, the smallest total after along any connecting path — the per-edge weights shipped in NEIGHBOR_STRUCTURE, the entirety of the RTI's program knowledge. Causality check: before the program is split, the validator builds the reaction and port graph of the whole federation and rejects any causality loop — a cycle along which a reaction’s output at some tag would depend on itself at that same tag (lfc 0.13 names the reactions: “Reaction triggers involved in cyclic dependency”). A cycle of federates with zero total delay is a different, weaker condition, and on its own it is not an error: when no reaction on it waits for its own output, the program is constructive, each tag has a unique solution, and the federates can reach it by exchanging presence and absence. The compiler marks such federates as members of a zero-delay cycle and gives their network senders port-absent reactions, and under centralized coordination the RTI releases them with PTAGs (Section 4.3)[36]. Two lines to remember: a causality loop is always an error; a zero-delay cycle is an error only between enclaves inside one program (Section 4.8), where the runtime has no PTAG to release it. Absence machinery: for every network sender, logic that emits PORT_ABSENT when a reaction that could have written a port completes without doing so. The coordination target property selects which shims are generated; same source, two protocols. Output: one binary per federate, the RTI compiled from bundled matching source, and a launcher script.

The launcher is more than a convenience and worth knowing before you debug a deployment that will not start. It brings up the RTI first, passing the federation ID and the number of federates it must wait for, then starts each federate with that RTI’s host and port — over SSH when the target declares a remote host, which is how a federation spans machines without a deployment tool. It then traps signals, so interrupting the launcher tears the whole federation down instead of leaving orphaned processes holding sockets. And it is worth being exact about what NEIGHBOR_STRUCTURE carries, because it is the entirety of the RTI’s model of your program: per federate, the number of upstream federates, their IDs, the minimum delay on each of those edges, and the number and IDs of its downstream federates. No port names, no reaction graph, no reactor hierarchy, no types. The grant algebra of Section 4 runs on that and nothing else — which is exactly why it can be reimplemented on a substrate that has no notion of a program at all (Section 9).

Inside a federate

A federate process runs worker threads (the ordinary LF scheduler), one listener thread per socket mutating shared state under a single mutex, and optionally user threads feeding physical actions. The scheduler walks this loop:

Refinements that make it correct: a federate with physical actions caps its NET at current physical time and keeps re-sending as time passes — the federate-side origin of the RTI's bounded-by-physical-time inference. An empty queue reports NET(∞), maximal information. And execution is gated by port knowledge: each network input port at the current tag is present, absent, or unknown; the scheduler computes a maximum-level cap from the first reader of each unknown port. Under a full TAG all ports resolve at once (a TAG means nothing more is coming) and the tag runs free; under a PTAG, workers advance level by level as each TAGGED_MESSAGE or PORT_ABSENT flips one port, and reactions that could read an unknown input are held back, together with the outputs they would produce, while every other reaction runs and sends its outputs — the concrete enforcement of a provisional grant: work proceeds as far as the known inputs allow, and the tag completes only when none is unknown. The decentralized variant is a small diff: the wait receives a clock deadline instead of a grant, the unknown→absent transition comes from a per-port safe-to-assume-absent (STAA) timeout instead of a message, and the impossible-in-centralized case — a message for an already-passed tag — routes to the violation handler. One invariant unifies both modes: logical time never passes a tag until every network port at that tag has a resolved status; the modes differ only in who may resolve it.

The cap has a name and a condition variable. In the code the level cap is max_level_allowed_to_advance (MLAA); a worker that reaches a reaction at or above it blocks on lf_port_status_changed, and every event that could resolve a port — an arriving message, a PORT_ABSENT, a full TAG, an STAA timeout, the news that an upstream transient is absent — broadcasts on that same condition variable after updating the port. The whole tri-state discipline is one integer and one broadcast.

The STAA side is a thread, and its details are not cosmetic. In decentralized mode a dedicated thread walks a code-generated array of STAA entries kept sorted by offset — the generator has already subtracted each connection’s after delay from the stored value, so the sort is by the quantity that actually governs the wait. For each entry it waits until the current tag’s time plus that offset plus the federate’s own STA offset, then marks every still-unknown port of that entry absent. Three refinements matter. When the computed wait falls below five times the runtime’s minimum sleep interval, that much is added to it, because a zero STAA with a zero STA would otherwise spin without ever releasing the environment mutex and, in the source’s own words, cause chaos — the cost is a slightly late absence decision, never a late event. Any change of the current tag aborts the walk and restarts it, since the offsets are relative to the tag being decided. And a port whose upstream is a transient known to be absent is marked absent immediately, without waiting out its timeout: membership information is strictly better evidence than a clock, and Section 3.2’s membership messages exist to deliver it.

§ 09 / into the fabric

Hardware–software codesign

Jellum, Schoeberl, Lee, and Orlandic (ACM TRETS 2024)[9] extend LF with a Chisel target (whole programs as synthesized logic) and a Codesign target (one program mixing C++ reactors on the CPUs and Chisel reactors on the FPGA of a Zynq-class system-on-chip, SoC), implemented by a hardware runtime, reactor-chisel. The claim is not another high-level-synthesis flow; it is that the reactor model of computation (MoC) itself — deterministic, timed, concurrent at arbitrary granularity, open to asynchronous inputs — is the right shared abstraction, where OpenCL/SYCL admit nondeterminism, high-level synthesis (HLS) cannot express timing, ReconOS inherits shared-memory races, and Bluespec's guarded atomic actions are nondeterministic by design.

9.1 — Why Scala: elaboration, not execution

Chisel is a hardware construction language embedded in Scala[10]. No Scala runs at runtime; a Chisel design is a Scala program that, when executed, elaborates a circuit graph, which FIRRTL lowers to Verilog. This generator model is exactly what an LF backend needs: lfc emits a Scala program that instantiates parameterized reactor-chisel library classes — Reaction, InputPort, Connection, TriggerGenerator — and Scala's type system checks token types and port widths at elaboration. Reaction bodies are user-written Chisel between the same {=…=} brackets as any target, against a mirror API: lf_get, lf_set, lf_read/lf_write for state, lf_get_array/lf_set_array for bulk ports, lf_time_logical(), lf_time_physical().

9.3 — reactor-chisel microarchitecture

The runtime is glue logic wrapping user modules, plus one central scheduler; tokens act as a virtual clock, enabling modules in a predefined order.

Tokens. Three classes, all carrying a tag and an absent bit. PureToken: no payload — timer triggers and inter-reaction precedence. SingleToken: one value on wires sized to the full datatype (narrow types only). ArrayToken: bulk data buffered in RAM, accessed by address and length.

Interfaces. Four ready/valid channels — read request, read response, write request, write data — compose into TokenReadMaster/Slave and TokenWriteMaster/Slave, plus a fire signal marking consumption or production complete. Array tokens use the request channels' address/size fields; single and pure tokens leave them idle.

The Reaction module. Everything the programmer writes is enclosed in a generated wrapper whose core is a small finite-state machine (FSM):

Precedence as a token ring. In-reactor reaction ordering has no scheduler thread to enforce it, so the compiler synthesizes it as dataflow: pure-token connections chain reaction 1→2→3, and a back-edge from the last to the first is initialized with a single pure token — reaction 1 cannot take its next token until reaction 3 finishes the current one. Mutual exclusion becomes an initialized buffer, exactly as in SDF; that exclusivity also lets all reactions' state-variable ports multiplex onto one read and one write port into flip-flop storage. A semantic landmine follows from the FSM: registers declared inside a body reset every firing (they are locals); only LF state persists across tags. Chisel muscle memory will betray you here.

Ports and connections. An InputPort is an arbiter fanning one token stream to N in-reactor reactions plus M contained reactors (M+1 parallel read channels, discovered by walking the containment hierarchy); an OutputPort joins — reactor semantics permit only one write channel. A Connection is the buffering memory between ports: flip-flops for single tokens, on-chip block RAM (BRAM) for arrays between hardware reactors, off-chip DRAM when the connection crosses to software. One writer, many independent readers, a coarse state machine on the fire signals.

TriggerGenerator: the RTI in miniature. All tokens originate here. It holds the two queues — the static timer/startup/shutdown schedule and the physical-action FIFO — each exposing the tag of its next token as a NET, and a Scheduler submodule that fires the lower NET when permitted by an external TAG input compared against the current time. For standalone FPGA programs the TAG is hardwired to a forever tag: a pure-hardware program grants itself everything and the coordination logic optimizes to nearly nothing. A queued copy of each released tag drains out as LTC once it has fully propagated through the reaction graph. Those three signals are about to become very familiar.

9.4 — The Codesign target: federation over AXI

Mark a reactor instance @fpga and connect it normally; the toolchain regenerates all interface logic. Coordination between the CPU-side runtime and the FPGA is, verbatim, a subset of the coordination scheme used in distributed LF: the FPGA publishes NET and LTC through status registers; software returns TAG through a control register; the TriggerGenerator does not release the next token until it holds a TAG greater than its NET. The transport is a bank of control/status registers (CSRs) on an AXI4-Lite slave instead of a TCP socket — a “message” is a register access at bus speed — and the coupling is bidirectional: a pending event in a hardware reactor stalls software from passing its tag, and vice versa, which is precisely what guarantees, e.g., that a fusion reactor sees an interrupt-driven proximity sensor (CPU), a 100 Hz camera pipeline (FPGA), and an asynchronous wheel encoder (FPGA) in timestamp order.

The data plane, quantified. Array semantics are write-before-read: a connection is a double-buffered RAM, and the downstream is not triggered until the upstream's fire. Measured on-fabric: a 1-element round trip costs 5 cycles; write 256 words and the downstream triggers at 260; write and read all 256 and it is 515. Pipelines of small-token reactors sustain one token per 7 cycles regardless of depth (3 cycles of FSM wrap around a 1-cycle body, plus a downstream-completion guard protecting connection memories); planned FIFO tokens would trigger on first write and recover streaming. Design consequence: model streaming as chains of reactors with small tokens; keep fine-grained pipelining inside one reaction body in raw Chisel.

9.7 — Partitioning judgment

The mechanism is one attribute; the decision is engineering. Distilled from the numbers: granularity floor — a hardware reaction should encapsulate hundreds of cycles of work (a filter kernel, an FFT, a frame transform); at one cycle of body the 7-cycle cadence is a 700% coordination tax, so LF coordinates between accelerators, raw Chisel pipelines within one. Boundary tax — minimize chatty crossings: one composed array per period beats five scalars, and never place the SW/HW boundary inside a tight feedback loop. Forced placements — FPGA: pin-connected @external ports, sub-microsecond stimulus response (timer-triggered hardware reactions fire with zero cycles of lag, via static early release from the token queue), dense data-parallel math. CPU: anything needing logical actions (banned in hardware), dynamic memory, OS services, or irregular branching. The coupling is the cost of the guarantee — bidirectional stalling secures global timestamp order; subsystems that genuinely need no ordering with the rest should bypass the reactor graph via raw @external wires rather than pay for it. And because the default build is a co-simulated single executable, the partition is an experimental variable: move @fpga, rebuild, measure lag, iterate — Vivado only when it stabilizes.

9.8 — Worked example: the sensor-fusion partition

Make the guidance concrete with the paper's motivating application: a robot fusing three sources — an interrupt-driven proximity sensor, a 100 Hz camera, and an asynchronous wheel encoder — where the fusion step must observe them in timestamp order. The natural partition puts the camera pipeline on the FPGA (dense per-frame math, one array token per period), the wheel encoder on the FPGA (a physical action wired to a pin through an @external port, so pulses are timestamped in hardware at the moment they occur rather than after an interrupt-latency delay), and the proximity sensor plus the fusion logic in software (irregular control flow, occasional allocation). Two connections cross the boundary per period, not six; the fusion reactor's inputs are ordered by construction rather than by hopeful timestamp comparison in application code; and the bidirectional NET/TAG/LTC coupling means a late software fusion step visibly stalls the fabric rather than silently letting frames overtake encoder pulses. A manual implementation in C++ and VHDL must enforce this ordering explicitly at each software–hardware interface. The Ingenuity incident cited in Section 1 separately illustrates the consequences of associating sensor data with incorrect timestamps.

9.9 — What a hardware RTI would have to implement

The TriggerGenerator of Section 9.3 is called “the RTI in miniature” advisedly: it is the degenerate case, one node whose TAG input is hardwired to forever. Between it and the grant algebra of Section 4 lies a question this document has been circling and should state plainly — what would it take to synthesize the whole decision function, so that n on-chip federates coordinate without a CPU in the loop? Section 5.3 sets that question against micro-LF, in which no RTI takes part in the advance of logical time.

Most of Section 4 carries over unchanged, and one part of it becomes simpler. The min-delay matrix of Section 4.5 is built lazily in software because federates join and resign at runtime; on a chip whose topology is fixed at synthesis the same matrix is a constant, so the lazy relaxation, its cache-invalidation logic, and the cycle detection are all computed at elaboration time, and what remains in the hardware is a ROM of n×n tags and two flag bits per node. EIMT (Section 4.6) becomes a min-reduction over one column of that ROM — node e's upstreams are the rows with a finite entry in column e — against a register file of per-node NETs: a tree of comparators of depth log n, one clock domain, no search. The trichotomy of Section 4.9 is combinational: three comparisons and a multiplexer over the same tag width used everywhere else in the fabric.

What disappears is the transport and the failure model. Sockets, the byte protocol, and the listener thread per federate become wires and registers, as they already do across the AXI boundary in Section 9.4. Clock synchronization (Section 6) is no longer needed: there is one oscillator, so E = 0, as Section 10 explains. Transient federates (Section 3.2) and FAILED handling have no meaning when membership is decided by a bitstream. The end of a run is another matter, and it remains: a federate that finishes still leaves with RESIGN, and a node whose upstreams have all left must still be told that nothing more can arrive, so the disconnection branch of Section 4.9 stays in its termination role — the FOREVER grant — while its transient variant disappears. Static membership fixes who joins, not when the run ends. The coarse RTI mutex of Section 4.10 does disappear, and with it the argument that made it necessary — there is no lock order that can be violated when the decision is a combinational function of registers sampled on one edge.

Two aspects become harder, and they are where the engineering effort lies. First, the cost model inverts. In software the dominant term is the notification fan-out (Section 4.10): one NET triggers a decision per transitive downstream, serialized under one lock, which is what makes the broker a bottleneck. In hardware those n decisions are independent and run at once, so the fan-out stops costing time per message — a message reaching one node and one reaching all of them take the same fixed time — and starts costing area; the fixed time itself still grows with the size of the federation the hardware is built for, as the next paragraphs show — n comparator trees plus O(n²) tags of matrix storage, which is what bounds n long before throughput does. The interesting quantity is no longer operations per NET but LUTs per federate. Second, PTAG propagation (Section 4.3) is recursive in software and has no visited set at all: it stops because a node already granted the tag returns at once. (The heap-allocated visited array belongs to the other walk, the downstream notification after an LTC, Section 4.10.) Recursion whose only bound is an argument about tag values is exactly what Section 9.2 bans, so the hardware version must be a fixed-point iteration over bit vectors, with an explicit visited set and a step count bounded by n — and that bound is available only because the topology is known at synthesis time. The static topology that made the matrix free is the same fact that makes the one genuinely recursive part of the protocol synthesizable. Building that decision function in hardware is the question the rest of this section examines.

Pursuing it reveals three further issues. Each looks like a detail, and each decides whether the hardware agrees with the software.

The software runs a cascade; the hardware takes a snapshot. The RTI handles a NET by evaluating the sender, then each transitive downstream in index order, then the DNET candidates; it handles an LTC by walking the downstreams depth-first. Each step can write state that a later step reads. A grant updates last_granted before the next node is judged; a PTAG sets off the upstream walk in the middle of the loop, so a node can be granted by the walk and then judged again by the loop; and EIMT quietly stores the start tag into any upstream it finds silent, so a node that has never sent a NET looks, from then on, as if it had. A hardware RTI evaluates every node at once against one copy of the state, so each of those writes has to become an explicit rule. Emission is masked to the set the software would have visited. When one node receives several grants in one step, only the strongest is emitted: a PTAG of g already authorizes every tag before g, so a TAG below it adds nothing. The start-tag write-back is applied at the end, and the startup window is run as an uncompared preamble. Comparing the two implementations then means comparing what the order cannot change: per node, the strongest grant, and the grants to different nodes as a set. One case the order does change is an equal-tag tie between a TAG from the walk and a PTAG from the node's own decision. The software can resolve it either way, because the walk tests the plain EIMT while the decision tests the tightened one, so the hardware has to pick, and it picks the weaker grant.

  1. One node, or all of them. s sends a NET. The software RTI judges its first downstream node, under the lock. How to read Figure 25. The software RTI judges the sender’s downstream nodes one after another, and each judgement sees what the earlier ones wrote. A hardware RTI judges every node at once against one copy of the state, emits only for the nodes the software would have visited, and merges the grants one node can receive in one step. “Fixed” means fixed for the size the hardware is built for; Figure 26 shows how it grows with n.

The matrix is read whole, every time. Evaluating all n nodes means reading every column of the min-delay matrix on every message. A block RAM hands over two entries a cycle; each reduction tree wants n. So the matrix is split into n shallow, wide banks, one per row, which is the shape distributed LUT memory fits and block RAM does not. The number of trees becomes the parameter that trades latency against area. With one tree per node, the latency is the log n claimed above. A single tree, which is what the rest of the design can afford, makes it linear in n again: still a constant fixed at synthesis, but no longer nearly free. The DNET computation reads the matrix by rows instead, and when its fast path does not apply it takes about n cycles, which bounds throughput rather than latency.

  1. Arrival and queue. m1 arrives and is accepted at once. m2 arrives while m1 is being handled and waits in the queue.
  2. K. From acceptance, evaluating every node takes exactly K = 24 cycles: this is the constant.
  3. K_max. A PTAG walk may follow, up to (n − 1)·z = 14 cycles, so every grant of a message has left by Kmax = 38 cycles after its acceptance.

What Figure 26 shows. “fixed” means fixed for the size the hardware was built for, and the wait in the queue is the part that is only bounded.

The in-transit queue becomes a small table. The priority queue of Section 4.11 supports only three operations: insert a tag if absent, remove everything up to a completed tag, read the minimum. In hardware each is one parallel compare over a few entries per federate, and since each message touches one destination, one bank of comparators serves them all. What hardware cannot do is grow the in-transit table. A full in-transit table cannot drop an entry, because the bound it carries would vanish while its message is still in flight. Merging entries is safe, but inside a zero-delay cycle it can slow progress to one microstep per round trip. So the synthesizable RTI treats overflow as an error: the one case in which it must refuse where the software allocates and accepts.

§ 10 / the substrate

InterPRET: making the assumptions theorems

Decentralized coordination (Section 5) and every deadline rest on bounds — the E, L, D of the decentralized inequality, the D inside every deadline. On commodity hardware those are measured guesses: caches, branch predictors, and out-of-order execution trade predictability for average-case speed, and cache-coherent multicore makes tasks non-composable — a write on one core evicts a line on another, so tasks with no data dependency still perturb each other's timing. InterPRET (Jellum et al., CPS-IoT Week 2023)[11] is the precision-timed (PRET)[17] answer: FlexPRET RISC-V cores interconnected by the S4NOC, an end-to-end time-predictable multicore whose stated destiny is to be programmed in LF.

10.1 — FlexPRET: the core

A five-stage in-order RV32I core[12] (the base 32-bit RISC-V integer instruction set) with no caches and no branch predictor. Two mechanisms recover throughput: fine-grained multithreading with a barrel register file (interleaved hardware threads eliminate pipeline hazards structurally), split into hard real-time threads (HRTTs, guaranteed a constant scheduling frequency — perfect temporal isolation) and soft real-time threads (SRTTs, opportunistically absorbing unused cycles); and timing instructions in the instruction-set architecture (ISA) — delay_until, wait_until, interrupt_expire — with nanosecond precision. Memory is scratchpads with constant access latency. The consequence, in worst-case-execution-time (WCET) terms: of the two classic analysis dimensions — the path problem (longest path through the code) and the state problem (which microarchitectural state maximizes time) — FlexPRET deletes the state problem by construction. Only the path problem remains, and it is tractable.

10.2 — S4NOC: the interconnect

Cores share nothing; they exchange single-word packets over a bidirectional torus of routers[13] whose every shared resource is allocated by a statically computed time-division-multiplexed (TDM) schedule — one packet per resource per cycle slot, hence no buffering in routers, no flow control, no contention, ever. The schedule for all-to-all communication on a 3×3 grid is ten slots of ten bits each. Worst-case message latency is a closed formula, L_noc = (2l + s + h) × p — network-interface (NI) latency, schedule length, hop count, clock period. The network interface is memory-mapped ready/valid queues with status bits.

10.3 — The rendezvous, and why it closes the loop

The paper's PingPong study exchanges values with non-blocking NoC calls; correctness requires the message to already be present at the receive — guaranteed purely by delay_until on both sides plus a statically derived offset. Every term is computable: sender worst case L_tx = c_tx × p × N_t (worst-case thread cycles × clock period × interleaved HRTT count — 40 thread cycles → 3200 ns on the quad-core config), receiver best case 1600 ns, NoC worst case (2×2 + 5 + 2)×20 ns = 180 ns, total L_send = 1780 ns — confirmed exactly on the FPGA. The analytical bound and the measurement coincide because no microarchitectural state remains to make them diverge. That number states the PRET thesis: on such a processor timing is fixed by the hardware design, not measured after the fact.

Recognize the shape: wait until physical clock ≥ tag + offset, then assume absence is the decentralized coordination protocol of Section 5. The difference is epistemic status. On a Linux cluster, E + L + D are estimates and the STAA violation handler exists because they will occasionally lie. On InterPRET, E collapses to zero on-chip (one oscillator), L is a formula, D is a path-only WCET — the fault case is provably unreachable. Decentralized LF on this machine is decentralized LF with its assumptions promoted to theorems. Follow-on work completes the circle: an LF runtime ported to FlexPRET[14] (HRTTs as isolated workers, delay_until as the tag wait, interrupt_expire as deadline detection, physical actions on real interrupts), and the Patmos + LF + Platin toolchain[16] demonstrating machine-checked WCET for reaction bodies. Numbers, for scale: one core costs 2,526 LUTs; the NoC's per-core share is 175; measured inter-core latency is 35–44 cycles with the 9-cycle jitter exactly decomposable into its two sources; NoC bandwidth reaches 291.5 of a theoretical 320 Mbit/s at 50 MHz. The chip also hosts software-defined devices — peripherals as programs on HRTTs, e.g. a bit-banged UART (serial port) sustaining 270,000 baud whose idle cycles SRTTs absorb.

§ 11 / one rule, four transports

The unifying invariant

Strip every layer to its skeleton and the same sentence remains: a component may advance to a tag only when it is safe to conclude that no earlier-tagged input can still arrive. The layers differ only in how safety is established.

Table 7 — how each layer establishes safety.

Decentralized federationPeer sockets + synchronized clocksAssumption: after > E + L + D, with a violation handler for when reality objects.

That is the actual intellectual content of the Lingua Franca project: one coordination algebra, implemented on ever lower layers — runtime, processor, logic — until every timing assumption becomes a proven bound.

§ 12 / appendix

Run it yourself

The experiments below use three small programs of your own writing — they are specified here, and complete solutions in C and Python, compiled with lfc 0.13.0, are in the tutorial edition and in the examples/ folder next to it. All three set tracing: true and share one shape: a federate A carrying a physical action as its “sensor” feeds B, and B feeds back to A. They differ in the feedback delay and the coordination mode, because each is designed to demonstrate one behaviour, and a program built to show grants cannot also show provisional grants:

  • FeedbackCentralized.lf — centralized coordination, after 200 msec on B→A, no delay on A→B. The cycle carries a delay, so it is not a zero-delay cycle, and the trace should show NETs, TAGs and LTCs but no PTAG. A is granted well ahead of its requests, since nothing B sends can reach it sooner than 200 ms later; B’s grants follow A’s NETs, which the physical action keeps revising.
  • FeedbackZeroDelay.lf — the same program with the after removed from B→A, so that A and B form a zero-delay cycle. It has to stay constructive (Section 7): in A, the reaction that consumes B’s input must not also write the output to B — declare it after the reaction that does, and give it no output — while B may answer its input directly. This is the program whose trace shows PTAGs: Sending PTAG rows in the RTI’s trace and Receiving PTAG rows in the federates’, whenever a member’s next event ties with what the cycle could still bring it. Let A’s input reaction write the output as well and the compiler rejects the program with a causality error — the boundary stated in Section 7, observed.
  • FeedbackDecentralized.lf — decentralized coordination, the delays of the first program plus after 100 msec on A→B (the margin that satisfies the safety inequality of Section 5), a timer in B so that B’s logical time advances on its own, a tardy body — the STAA violation handler — on every reaction to a network input, and @maxwait(0) on both federates: the default STA is forever, and without a bound each federate would wait for the other indefinitely.
# FeedbackCentralized.lf  — grants on the wire, no PTAG (the cycle has a delay)
lfc FeedbackCentralized.lf && ./bin/FeedbackCentralized

# FeedbackZeroDelay.lf    — B->A loses its after: a constructive zero-delay cycle, PTAGs
lfc FeedbackZeroDelay.lf && ./bin/FeedbackZeroDelay

# FeedbackDecentralized.lf — clocks instead of grants, A->B gains `after 100 msec`,
#   B gains a timer, network-input reactions gain tardy handlers, both get @maxwait(0)
lfc FeedbackDecentralized.lf && ./bin/FeedbackDecentralized

Experiments: convert the .lft traces with trace_to_csv (reactor-c, util/tracing). In the first program, confirm that grants appear and PTAGs do not; in the second, find the PTAGs and match each to the branch of the decision that produced it; in the decentralized run, confirm that the grant rows vanish. To see an STAA violation, shrinking the margin is not enough by itself: a violation needs a message that reaches B after B has already advanced past that message’s tag. Shrink the 100 ms margin to 1 msec, keep B’s timer running, and make A’s sending reaction slower than the slack that remains (for instance, let it sleep for 50 ms of physical time before it sets the output); the handlers should then fire instead of the program silently corrupting. Whether and how often they fire still depends on execution conditions — load, clock error, network latency — and that is the lesson: the decentralized guarantee holds only within its bounds, and the handler is what runs when a bound is exceeded. For the RTI's live reasoning, build it in debug (cmake -DCMAKE_BUILD_TYPE=DEBUG in core/federated/RTI) and match each printed grant to its branch in tag_advance_grant_if_safe().

Everything in this section was checked on 28 September 2026 with Lingua Franca 0.13.0 on Linux (Java 21, gcc, CMake, Python 3.11). The tools change between releases: when a command here disagrees with the release you install, the documentation at lf-lang.org is right. The example programs of the tutorial edition, in C and in Python, are also in the examples/ folder next to it.

14.1 — Installing

  • Prerequisites. Java 17 or later (the compiler is a Java program), a C compiler and CMake. The C toolchain is needed for the Python target too: it generates a C extension module around your Python code and builds it with the same compiler and CMake, so the Python target also needs Python 3 with its development headers (on Debian and Ubuntu, python3-dev).
  • Command-line tools. curl -Ls https://install.lf-lang.org | bash -s cli installs lfc (compiler), lff (formatter) and lfd (diagrams); append nightly for the nightly build. Alternatives: the release archive from the lf-lang/lingua-franca GitHub releases (for example lf-cli-0.13.0-Linux-x86_64.tar.gz, unpacked with its bin/ on the PATH), nix shell nixpkgs#lingua-franca, or yay -S lf-cli-bin on Arch. Check with lfc --version.
  • VS Code. Quick Open (Ctrl+P), then ext install lf-lang.vscode-lingua-franca; the extension is also on Open VSX and works in VS Code–compatible editors such as Cursor. It adds syntax-directed editing, a diagram view (the icon at the top right of the editor) and two commands, Lingua Franca: Build and Lingua Franca: Build and Run. For the Python target, install Pylint 2.12.2 or later to enable linting. The Epoch IDE of earlier releases is no longer listed on the installation page.

On Windows, in this order. The tools and every build run inside Linux, under WSL; Windows only hosts the editor.

  1. Prepare the Linux environment. In PowerShell opened as administrator, wsl --install -d Ubuntu; restart when asked, open Ubuntu from the Start menu, and create the Linux user it asks for.
  2. Install the build tools inside Ubuntu, not on Windows: sudo apt update && sudo apt install -y openjdk-17-jdk build-essential cmake python3 python3-dev git curl.
  3. Install Lingua Franca inside Ubuntu with the curl … | bash -s cli command above, and keep your programs in the Linux file system (for example ~/lf/src/) rather than under /mnt/c, where builds are much slower.
  4. Connect VS Code to WSL. On Windows, install VS Code and its WSL extension. Then either run code . from the project folder in the Ubuntu terminal, or use WSL: Connect to WSL and File › Open Folder in VS Code. The window’s bottom-left corner then reads WSL: Ubuntu.
  5. Install the Lingua Franca extension in that window. The Extensions view offers Install in WSL: Ubuntu; an extension installed only on the Windows side does not see the Linux tools.
  6. Check which tools you are using. In the window’s integrated terminal, which is a Linux shell, run which lfc gcc cmake python3 and lfc --version. Every path should be a Linux path (/home/…, /usr/bin/…). If a Windows installation appears instead, or the version differs from the one you installed, fix the PATH in ~/.bashrc before building.

14.2 — Building and running one program

Keep sources in a src/ folder. lfc src/Hello.lf creates src-gen/ (the generated C or Python) and bin/ (an executable, or a launcher script for Python) next to src/; run ./bin/Hello. Options worth knowing: -c cleans before building, -n generates code without compiling it, -q silences the target compiler, --logging=debug sets the runtime’s log level, --tracing turns tracing on without editing the file, and -o changes the output root. lff src/ formats every program in place (-c only checks, -d prints instead of writing), and lfd src/Hello.lf writes Hello.svg, the reactor diagram, into the current folder. In VS Code, Build and Run does the first two steps at once.

14.3 — Running a federation

For a federated reactor, lfc writes one program per federate under fed-gen/Name/, builds the RTI from the reactor-c source it bundles into fed-gen/Name/bin/RTI, and puts a launcher in bin/Name. The launcher starts the RTI, then every federate, and stops them all on Ctrl+C; -l sends each process’s output to a log file, -x opens them in tmux panes, and -s sets how long it waits for the RTI. To launch them manually, start fed-gen/Name/bin/RTI -i id -n N and then each fed-gen/Name/bin/federate__x -i id with the same federation id. For decentralized coordination, set coordination: decentralized in the target, give federates a bound with @maxwait(…) (the default is forever) or connections one with @absent_after(…), and add a tardy {=…=} body to reactions that must handle late messages; lfc 0.13 still accepts the older STAA(…) {=…=}.

14.4 — Traces

tracing: true in the target (or lfc --tracing) makes every federate and the RTI write a binary .lft file into the folder they run in. The converters are part of reactor-c: git clone https://github.com/lf-lang/reactor-c, then make trace_to_csv in util/tracing (make install builds and installs all three converters and needs libcurl). trace_to_csv rti.lft writes rti.csv, one row per event (Sending TAG, Receiving NET… with logical and physical times in nanoseconds), and rti_summary.csv with the counts. A microstep printed as -1 is UINT_MAX.

§ 15 / fixed points

Fixed points, dependency graphs and federated execution

Three claims in the main text rest on order theory and graph theory that the main text only states. This appendix states each one precisely, with its hypotheses, and states how it is justified.

  1. The closure terminates and is exact (Section 4.5). Delays are tags with non-negative time, combined along a path with the tag addition ⊕ (Section 4.4), which is associative, monotone in each argument, and satisfies x ≤ x ⊕ d for every delay d. Under these hypotheses the relaxation makes finitely many improvements, whatever order it relaxes in, and ends at the matrix of least path delays: for i ≠ j, the least delay over simple paths from i to j; on the diagonal, the least delay over simple cycles through i; FOREVER where there is none. The argument is in Section 15.3.
  2. A constructive program has exactly one behaviour at each tag (Section 4.14, Section 7). Fix a tag, the state of every reactor and the events present at that tag, and assume that every reaction body computes its outputs deterministically from its inputs and state. Resolving port statuses is then a monotone function on an order of finite height, with a least fixed point that Kleene iteration reaches (Section 15.1). If the reaction graph has no cycle, that least fixed point leaves no port unknown and it is the only fixed point, so the behaviour at the tag is unique (Section 15.3). Acyclicity, the compiler’s static check, is sufficient for constructiveness but not necessary: a cyclic graph can still resolve every port for particular inputs, and Lingua Franca rejects it anyway[33],[34].
  3. Grants only climb (the opening of Section 4). For each federate, from the moment it joins until it leaves, the tags of the grants the RTI sends it, TAG and PTAG taken together, strictly increase, and no grant is withdrawn. This is not a theorem of order theory but a property of the implementation: every path that sends a grant, including the queue of delayed grants (Section 3.2), first drops any tag that is not above both last_granted and last_provisionally_granted (checked in reactor-c at commit ccd0512[5]). It makes no claim about optimality: the appendix does not claim that a grant is the largest tag that could be proved safe (Section 15.3).

The rest of the appendix serves these three claims: definitions (Section 15.1), the two dependency graphs (Section 15.2), the three computations (Section 15.3), and the same computations in other settings (Section 15.4). The worked examples are the federation of Section 4.13 for the min-delay matrix (Figure 31) and for the joint picture that closes Section 15.3, a small function on a chain for Kleene iteration (Figure 29), and the feedback pair of Figure 20 for the value of a tag (Figure 33). Figures 32 and 34 show the two proof sketches of Section 15.3. Results from the literature — Tarski’s theorem, Tarjan’s algorithm — are stated with a citation and not proved. Arguments specific to this document are proof sketches, folded in blocks whose titles begin with “Why”; they are sketches, not formal proofs. All three claims hold relative to the inputs that come from physical time, listed at the end of Section 15.4. Section 4.14 traces the origin of the ideas; this appendix shows how they work.

15.1 — Orders and fixed points

A partial order ⊑ on a set is reflexive, antisymmetric and transitive; two elements may be incomparable[47]. Two orders run through this document. Tags are totally ordered, by time and then microstep (Section 4.4). The status of a port at one tag is ordered by information: unknown lies below both present and absent, and those two are incomparable. It is a flat order: a status can only rise, and only once — which is precisely the rule of Section 8, where a port that has been resolved never becomes unknown again. Figure 28 shows both, with the order on pairs of ports that an iteration actually climbs and the order on delays used below.

The steps of Figure 28

  1. Tags. Any two tags are comparable: first by time, then by microstep. Among finite tags none is largest; the runtime represents “never” with the sentinel FOREVER_TAG, placed above them all.
  2. One port. At one tag a port is unknown, present or absent. Unknown lies below both; present and absent are incomparable, and neither can turn into the other.
  3. Two ports. Pairs compare port by port. ?? is the bottom; the four pairs with both ports known are maximal, and no element lies above all of them. The green path is the constructive run: p becomes present first, then q.
  4. A path delay. Read by information, FOREVER (no path known) is the bottom and a smaller delay lies higher. The entry S→C stays at FOREVER for two iterations and becomes 10 ms in the third.

What Figure 28 shows. The two fixed points built in this appendix iterate on orders like (2)–(4): each has a least element, and an iteration can reach only finitely many values in it, which is all the Kleene iteration needs. Tags (1) play a different role. Among finite tags none is largest, and the runtime adds FOREVER_TAG as a sentinel above them all; neither fact decides whether a run ends. A finite program stops; a long-running federation keeps deciding because new events keep arriving (Section 15.3).

A function f on an ordered set is monotone if x ⊑ y implies f(x) ⊑ f(y): more information in never means less information out. A fixed point is an x with f(x) = x, and the least fixed point is the one below all others. Tarski’s theorem guarantees that a monotone function on a complete lattice has a least fixed point[45]. For the finite orders used here there is a constructive route, usually credited to Kleene: start from the bottom element and apply f until nothing changes. The sequence ⊥, f(⊥), f(f(⊥)), … climbs, and in an order of finite height it must stop; where it stops is the least fixed point (Figure 29). The flat port order is not a lattice (present and absent have no common upper bound), but it has a least element and no infinite chains, which is all the iteration needs; this is the setting of the synchronous languages[33],[34].

Why the iteration finds the least fixed point

Let x be any fixed point. ⊥ ⊑ x, and if fk(⊥) ⊑ x then, by monotonicity, fk+1(⊥) ⊑ f(x) = x; so every element of the sequence lies below every fixed point. The sequence is increasing (⊥ ⊑ f(⊥), then apply monotonicity again), so in a finite-height order it reaches some y with f(y) = y. That y is a fixed point below every fixed point: the least one.

The steps of Figure 29

  1. A monotone function. f is defined on the chain 0 to 6, and the dots are the pairs (x, f(x)). Moving right never moves a dot down: that is monotonicity.
  2. Fixed points. Where a dot lies on the diagonal, f(x) = x: at 3, 5 and 6. The least is 3.
  3. The Kleene iteration. Start at the bottom, 0. f(0) = 2, f(2) = 3, f(3) = 3: the value repeats, and the iteration stops at 3.
  4. Why the least. By induction with monotonicity, every iterate is at or below every fixed point, so the first value that repeats lies below 5 and 6 as well.
  5. Without monotonicity. g sends 1 to 2 but 2 to 1. Its iteration climbs and falls back forever, and g has no fixed point to find.

How to read Figure 29. In the Kleene iteration, each vertical step applies f, and each dashed horizontal step carries the result to the diagonal, where it becomes the next x.

What Figure 29 shows. What makes the iteration stop at the least fixed point is monotonicity, a property of f at two comparable inputs (x ≤ y implies f(x) ≤ f(y)), not the fact that the sequence only climbs. Change f(2) to 4 and the sequence 0, 2, 4, 5, 5 still only climbs, yet stops above the fixed point 3. For the min-delay matrix, one relaxation step is monotone because min and ⊕ are (Section 15.3); for ports, a reaction whose inputs are resolved produces the same outputs however many other ports are resolved. The rule of Section 8 that a resolved port never becomes unknown again describes how the runtime updates its state; it is a different property from the monotonicity the proof uses.

For path delays the useful direction is downward: a delay only improves by getting smaller, the iteration starts from FOREVER (“no path”), and the least fixed point in the information order, of the function F of Section 15.3 that includes the direct connections, is the matrix of smallest delays (step 4 of Figure 28). It is the same theory with the order read upside down.

15.2 — Dependency graphs

A Lingua Franca program has two dependency graphs, and it matters which one is meant.

  • The reaction graph has a node per reaction and an edge wherever one reaction can affect another within the same tag: from a reaction that writes a port to the reactions that read the port it is connected to without delay, and between reactions of one reactor in declaration order. A connection with an after delay, or a scheduled action, adds no edge inside a tag. The compiler builds this graph for the whole federation and checks it (Section 7); within one program its topological order gives the levels of Figure 3.
  • The federate graph has a node per federate and an edge per connection, weighted by the least delay on it. It is what NEIGHBOR_STRUCTURE carries (Section 3.3, Section 7) and all the RTI ever sees.

Cycles are what separate the two. A strongly connected component is a maximal set of nodes that can all reach one another (a single node lies on a cycle only if it has an edge to itself); Tarjan’s depth-first algorithm finds all of them in time linear in the size of the graph[46], and contracting each component to one node leaves an acyclic graph. In the reaction graph a component that contains a cycle — more than one node, or one node with an edge to itself — is a causality loop, an error. In the federate graph a component is allowed; one whose internal paths have zero delay is a zero-delay cycle, which the RTI handles with PTAGs (Section 4.3). The same program can have a cycle in the federate graph and none in the reaction graph, and that is exactly the constructive zero-delay cycle.

On the federate graph, the least delay between every pair of nodes is an instance of the algebraic path problem: combine the delays along a path with the tag addition ⊕, and choose between paths with min[39]. The operator ⊕ is associative and monotone but not commutative (Section 4.4), which is why delays are accumulated in path order; associativity and monotonicity are all the relaxation needs.

The steps of Figure 30

  1. The reaction graph. Reactions of the example federation, with the dependencies that hold inside one tag: port to port across a connection without delay, and declared order inside a reactor. The after 10 ms connection to C adds no edge within a tag.
  2. No cycle. s1 → a1 → b1 → a2 ends, so the graph is acyclic and every tag has a least fixed point with every port known.
  3. The federate graph. Federates, the connections between them and the least delay on each, as NEIGHBOR_STRUCTURE reports them — all the RTI knows.
  4. A strongly connected component. A and B reach each other at zero delay: a zero-delay cycle of federates. It is legal because the reaction graph has no cycle, and the RTI releases it with PTAGs.

What Figure 30 shows. The compiler judges the left graph, the RTI works on the right one, and a zero-delay cycle on the right is legal exactly when the left has no cycle.

Three computations take place while a federation runs, by different parties and over different orders. Two are fixed points in the sense of Section 15.1, and this appendix builds them explicitly. The third, the RTI’s advance of time, is better described as a safe, monotone advance, and it is kept apart.

The structure. Let E be the matrix of direct connections, with FOREVER where there is none, and let F(D) = min(E, D ⊗ E), where (D ⊗ E)[i][j] is the minimum over u of D[i][u] ⊕ E[u][j]: a path to j is either one connection or a path to some u followed by the connection u→j. Starting from the all-FOREVER matrix ⊥, the bottom of the information order, F(⊥) = E, and the k-th round gives the least delays over paths of at most k connections (Figure 31). E has to be part of F: the function min(D, D ⊗ E) alone has ⊥ as a fixed point, so its least fixed point is not the closure. One round is monotone: if every entry of one matrix is at least as small as the same entry of another, min and ⊕ keep it so after the round. A round also only lowers entries, and each entry can take only finitely many values. With non-negative delays, the least delay between two different federates is reached by a simple path, one that repeats no node; a diagonal entry describes a non-empty path back to the same federate, and its least delay is reached by a simple cycle. Any further repetition adds a non-negative delay and never helps. A and B obtain their diagonal entries in iteration 2 exactly this way, through A→B→A and B→A→B; starting the diagonal at zero would erase the difference between a federate on a cycle and one that is not. So the relaxation stops, and where it stops is the least fixed point of F. The reference relaxes in a different order — upstream from each end node, recursing only when a path improves (Section 4.5) — and reaches the same matrix, because for a monotone step the order of the updates changes how long it takes, not where it ends.

Why any relaxation order stops, and stops at the least delays

It stops. A step changes an entry only when it strictly lowers it, and the reference recurses only after such a step. Delays have non-negative time and microstep, and pairs of natural numbers ordered lexicographically admit no infinite strictly decreasing sequence; with n² entries, the number of steps is finite.

It never undershoots. Every value written into an entry is the delay of some walk of the kind the entry describes, possibly repeating nodes, so no entry drops below the least such delay. Removing a cycle from a walk never increases its delay: for a walk P·C·Q, P ≤ P ⊕ C, and monotonicity and associativity give P ⊕ Q ≤ P ⊕ C ⊕ Q. So the least delay over walks is attained by a simple path, or on the diagonal by a simple cycle.

It does not stop too early. Whenever an entry improves, the steps that could use it are examined again — the next round in Figure 31, the recursion in Section 4.5. So when nothing changes, the column for an end node satisfies d(u) ≤ delay(u→v) ⊕ d(v) for every connection u→v, with the end node itself counted at zero delay (for the diagonal, the path must first leave the end node). Walking back along a least simple path from its last connection to its first, and applying monotonicity at each connection, shows that the entry is at most that path’s delay. With the previous point, it equals it. Figure 32 follows the three steps on a small graph.

What Figure 32 shows. Termination comes from the order on tags, the lower bound from x ≤ x ⊕ d, and the upper bound from re-examining the connections after every improvement; the order of the updates changes the route to the answer, not the answer.

The value of a tag. At a tag, each federate’s runtime decides its reactions as their dependencies are resolved. A reaction runs when it is triggered and everything it depends on is resolved; when all its triggers are resolved as absent, it is not triggered and does not run. A port is resolved once no reaction that may write it can still change it: each such reaction has run or has been shown not to be triggered. This happens locally level by level, and across the network through messages and PORT_ABSENT (Section 8). That is Kleene iteration on the port-status order (Figure 33). If the reaction graph has no cycle at the tag, the least fixed point leaves no port unknown and it is the tag’s unique behaviour; if it has one, the iteration may stop with ports unknown, as in the loop variant of Figure 33, and the compiler rejects every such cycle rather than decide constructiveness input by input[33],[34]. Across tags, a delay on every cycle makes the whole execution a unique fixed point as well[35].

Why an acyclic reaction graph gives exactly one behaviour at a tag

Every port is resolved. Take a topological order of the reaction graph and suppose the iteration has stopped with some reaction undecided. The earliest undecided reaction in that order depends only on reactions that come before it, all decided, so every port it reads is resolved and it can be decided in the next round — contradicting that the iteration stopped. So every reaction is decided, and every port resolved.

It is the only fixed point. Every fixed point x lies above the least one, x0 (Section 15.1). In x0 every port is present or absent, and in the flat order nothing lies above present or absent except itself, so x = x0 port by port. Both steps assume that a reaction’s outputs are determined by its inputs and state at the tag; physical actions and clock readings enter as inputs (Section 15.4). The same induction over the topological order fixes values as well as statuses: each reaction, when decided, reads inputs whose values are already determined and, being deterministic, produces determined outputs and a determined new state. Figure 34 shows both steps.

The steps of Figure 33

  1. The order. At one tag a port is unknown, present or absent. Unknown lies below the other two, which are not comparable; a port’s status can only rise, and only once.
  2. Round 1. a1 is triggered by the timer and depends on nothing else at this tag, so it runs and writes p. It is the only reaction that may write p, so p is resolved: present.
  3. Round 2. b1 is triggered by p, now present, so it runs and writes q: present. Had a1 left p absent, b1 would not be triggered, and q would be resolved as absent without b1 running.
  4. Round 3. a2 is triggered by q and runs. In the next round nothing is left to decide and nothing changes: this is the least fixed point, and every port is resolved.
  5. The loop variant. If a2 may also write p, p is resolved only once a2 is decided; a2 waits for q, q for b1, b1 for p. After a1 runs nothing else can be decided: the iteration stops with both ports unknown.

What Figure 33 shows. A program is constructive at a tag exactly when this least fixed point leaves no port unknown. The compiler does not run this iteration: it rejects every cycle in the reaction graph, a structural condition that guarantees constructiveness at every tag and is stricter than constructiveness in general. Each round decides every reaction whose triggers and dependencies are resolved — it runs if a trigger is present, and is not triggered if all are absent — and resolves a port once no reaction that may write it is still undecided.

What Figure 34 shows. Acyclicity gives a total least fixed point, and totality gives uniqueness; the second step uses only the shape of the flat order, not the program.

Time. The RTI’s records are completions, next events and grants. Completions and grants only move forward: a grant is issued only when the safety conditions of Section 4.2 hold, the guards drop anything that is not an improvement, and nothing granted is taken back. Each message re-applies the safety test to the nodes whose answer it could change, so grants advance as evidence arrives. That is a safe, monotone advance. This appendix does not define it as the least fixed point of one function, and it does not claim that after each message every grant is at the largest tag that could be proved safe; either statement would need an argument specific to the algorithm. Whether a run ends is a separate question. In the model, tags are finite and none is largest; the runtime uses FOREVER_TAG as a sentinel for “never”; a program with a timeout, or with no further events, stops; a reactive federation that runs indefinitely keeps receiving events, and each may require new decisions. The one input that can move backward is a NET lowered by an earlier message, and the in-transit clamp exists so that no grant is issued that such a message would contradict (Section 4.11). Donovan et al. give a formal treatment of the coordination[36].

All three together. In the federation of Section 4.13, the structure is the matrix of Figure 31; at tag 20 the RTI’s safe advance grants PTAGs to A and B and a TAG to C at (30 ms − 1 ns, UINT_MAX); and A and B then reach the value fixed point of tag 20 between themselves, by exchanging a message and an absence notice, before either sends its LTC.

15.4 — The same computation elsewhere

  • Decentralized coordination. There is no RTI to advance time for the federates. A federate reaches “known” for a port by a message, by an absence notice from its peer, or by a timeout (Section 5): the timeout pushes the port to “absent” on the strength of the clock rather than of evidence, which is why a wrong assumption surfaces as a tardy message instead of a wait.
  • Enclaves. The same algebra inside one process (Section 4.8). A zero-delay cycle between enclaves is an error because the runtime has no PTAG to release it.
  • Inside a federate. The level-by-level execution with its maximum-level cap (Section 8) is the value iteration restricted to one federate’s reactions, stopped wherever a port is still unknown.
  • In hardware. The closure is the algebraic path problem that Rote solves with a systolic array[39]; the per-message question is one parallel evaluation of every node (Section 9.9).
  • Where fixed points stop. Physical time is an input, not a fixed point: physical actions take the tag of the moment they happen, grants for an absent transient are released by the clock (Section 3.2), and decentralized timeouts are clock decisions. The guarantees of this appendix hold relative to those inputs.
§ 16 / micro-lf

micro-LF: federated execution without an RTI

Section 5.3 compared the two coordination architectures on paper: the RTI of Section 4, which grants a tag once logical evidence excludes an earlier message, and micro-LF, whose federates decide locally from the tags they have received, a waiting bound written in the program and a synchronized clock. This section follows the second mechanism through a running federation of two federates. The facts about the implementation are those of Section 5.3 — reactor-uc at commit df7cfea and the micro-LF documentation[48],[49] — and are not repeated with every statement; the runs are this project’s own measurements, on one host, and are labelled as such. Paragraphs marked as interpretation are this document’s reading.

16.1 — From a program to federates

The program. the program Tardy.ulf of the tutorial edition (Example 16.1) has two reactors. Src counts on a timer of period 200 ms and sends the count; at count 3 its reaction holds the message back for 100 ms of physical time before setting the output, standing in for a slow computation. Dst has a timer with the same period and one reaction triggered by the timer and by the input, with a tardy handler. The federated reactor makes each instance a federate, marks src as clock-synchronization grandmaster with @clock_sync(grandmaster=true), gives dst the waiting bound @maxwait(50ms), and connects the two with no after. @platform("native") selects the POSIX platform and @timeout(900ms) stops both federates at the same tag. Two choices in the program matter for what follows. The connection has no logical delay, so message n carries the tag at which it was sent, (200(n − 1) ms, 0). And Dst has a timer of its own: it has to advance to every multiple of 200 ms whether or not a message arrives, so at each of those tags it has to decide whether its input is present.

What the compiler produces. The micro-LF compiler generates a separate C project for every federate and a launch script that starts one process per federate; no RTI process exists to be started[49]. Each federate’s program contains a FederatedEnvironment and, for every neighbor, a FederatedConnectionBundle: one network channel to that neighbor, and the FederatedOutputConnection and FederatedInputConnection objects of the connections that the channel carries. When the program names no interface, the channel is TCP on the loopback address[49]. The startup, shutdown and clock-synchronization coordinators are part of every federate, with their event buffers sized at compile time, as are the event queue, the reaction queue and the payload buffer of each input connection (Section 5.3). The decision examined in this section reads three fields of each FederatedInputConnection: last_known_tag, max_wait (the value of @maxwait) and the payload buffer. Figure 35 shows the result for Tardy.ulf.

The steps of Figure 35

  1. Reactors. src and dst are compiled into two independent programs, each containing only its own reactor and the generated main reactor of its federate.
  2. Environment. The FederatedEnvironment owns the scheduler, the event queue, the system-event queue for coordination traffic, and a PhysicalClock: the hardware clock plus an offset and a rate adjustment applied in software.
  3. Connections. A FederatedConnectionBundle per neighbor holds the network channel (here TCP; src is the server, dst the client) and the connection objects. The input connection holds the three fields the tag decision reads.
  4. Coordinators and messages. Every federate contains a startup coordinator, a shutdown coordinator and a clock-synchronization component; src is grandmaster. Tagged data and all coordination traffic share the one channel. Every buffer is sized at compile time.

What Figure 35 shows. Everything that Section 3 assigns to the RTI is either inside the federates or absent; there is no third process.

Two state machines behind the chart. The startup coordinator moves through five states named in the protocol itself: UNINITIALIZED, CONNECTING, HANDSHAKING, NEGOTIATING and RUNNING (Figure 37). The handshake response carries the sender’s current state, and that is how a federate decides between negotiating a start time with neighbors that are also starting and joining neighbors that are already running; a mixture of the two stops startup with an error[49]. Underneath, every network channel runs a state machine of its own (Figure 38). Its one interaction with the tag decision is a precise one: a channel that is not connected is skipped by acquire_tag, so the inputs of a lost neighbor are treated as absent rather than awaited, and every change into or out of the connected state wakes the scheduler so that the decision is taken again.

The steps of Figure 37

  1. Connecting. All channels are opened at once; the coordinator waits, re-checking at the channels’ expected connection time, until every one is connected.
  2. Handshaking. A request goes to every neighbor; every response carries the sender’s coordination state, which decides the next transition once all responses are in.
  3. Negotiating, then running. When all neighbors are still starting, the federate runs longest_path rounds of start-time proposals, keeps the maximum, and after the last round schedules startup reactions and timers at the start tag.
  4. Joining, or failing. When all neighbors are running, the federate requests the start time and joins at the largest reported logical time plus 50 ms, stepping its physical clock to it (policy JOIN_IMMEDIATELY or JOIN_TIMER_ALIGNED). What Figure 38 shows. A lost neighbor does not stall its receivers: acquire_tag waits only for inputs on connected channels, so from the receiver’s side a disconnected neighbor is treated as having nothing to send.

16.3 — Following one tag

Consider dst at the tag g = (400 ms, 0), with @maxwait(50ms). The steps below follow the scheduler’s state machine of Figure 40; the outcomes were measured, and Figure 41 places them on dst’s physical timeline.

The steps of Figure 40

  1. Select and sleep. The loop takes the earliest of the event queue and the system-event queue, and sleeps until its physical clock reaches the tag’s time. notify() interrupts the sleep and the loop selects again. System events are handled directly and do not wait for inputs.
  2. Acquire and wait. For a tag event at g, every input on a connected channel whose last_known_tag is below g contributes its max_wait; W is the largest. If W is positive the loop waits until g.t + W. A message that arrives interrupts the wait; the loop selects again, possibly an earlier tag, and the deadline for g stays where it was.
  3. Commit. When W is zero or the deadline has passed, the loop commits g: it pops the events at g and runs the triggered reactions in level order; inputs not received are absent. A reaction whose triggering input carries a different intended tag runs its tardy handler, or its body if it has none.
  4. Receive: in time. The channel’s receive callback computes the message’s tag, the sender’s tag plus the connection’s after. If it is later than the current tag, the event is scheduled, last_known_tag rises to it, and the loop is notified.
  5. Receive: too late, or no room. If the tag is not later than the current tag, the runtime records a safe-to-process violation and schedules the event at the current time with the microstep plus one, keeping the intended tag. A full payload pool drops the message and leaves last_known_tag unchanged; a decoding error or a full event queue drops it but still advances last_known_tag.

What Figure 40 shows. The only inputs to the decision are local — the queues, the per-input records and the clock — and the only coupling between the two machines is the event queue, the last_known_tag fields under their locks, and notify().

Step 1 — the clock reaches the tag

The timer event at g is the head of dst’s event queue. The scheduler sleeps until the physical clock reads 400 ms after the start time and then calls acquire_tag(g)[49].

Step 2 — the input is unresolved, so the federate waits

The last message on the input was message 2, so last_known_tag = (200 ms, 0) < g: the input is unresolved. It is the only one, so W = 50 ms and the federate sleeps until its clock reads 450 ms. That instant is an absolute deadline: a message arriving earlier interrupts the sleep, the scheduler re-examines its queue, and a second call to acquire_tag computes the same deadline (Section 5.3).

Step 3 — nothing arrives: the federate commits, the input absent

src is still holding message 3, so the sleep runs to 450 ms and dst commits g. The reaction runs on the timer with the input absent, and its physical lag — the clock minus the tag’s time — is 50 ms, exactly W. From now on, g is in dst’s past.

Step 4 — the late message

At about 500 ms message 3 arrives, tagged (400 ms, 0). The tag is not later than dst’s current tag, so it cannot be scheduled: the runtime logs that it tried to schedule an event into the past, reports a safe-to-process violation and schedules the event at the current time with the microstep increased by one, (400 ms, 1), keeping (400 ms, 0) as its intended tag. At (400 ms, 1) the input is present with an intended tag different from the current one, so the scheduler runs the reaction’s tardy handler instead of its body; the handler printed the value, the intended tag and the tag at which it ran[49].

What the run shows. The value is not lost and the violation is not silent: the program sees it, at a defined tag, with the tag it was meant for. What the violation does change is the logical behaviour. At (400 ms, 0) the reaction saw the input absent; had the bound held, it would have seen 3 at that tag. Under micro-LF’s decentralized coordination the behaviour of a federated program is the behaviour defined by its tags as long as the timing bounds hold (Section 5.3), and a tardy handler is where the program states what to do when they did not.

16.4 — What absence costs, and choosing W

Absence is paid for in time. The fourth row of Table 11 is the cost of the design choice noted in Section 5.3: the protocol carries no message that reports absence, so a federate learns that an input is absent at g in one of three ways — a later-tagged message on the same connection, the passage of its clock to t + W, or the joining announcement of a neighbor. In the measured runs the second is what happened at 200 and 600 ms. The first was visible in a run with @maxwait(500ms) and the sparse sender: at the tag 200 ms dst did not wait until 700 ms, but committed at 500 ms, when message 3, tagged 400 ms, arrived and established that nothing tagged 200 ms would follow on that connection. A sender with nothing to say therefore delays its receivers by up to W at every tag at which they have something to do; a sender that stops altogether delays them by W at every such tag for as long as its channel stays connected (inputs on a disconnected channel are not waited for).

The same question under centralized coordination. In Section 4 the absence of a message is established by logical evidence: the upstream federate’s NET and LTC tell the RTI that it will produce nothing earlier, and the RTI grants the tag (Sections 4.2, 4.6). The cost of that evidence is a round trip through the RTI and the RTI’s serialized decision (Sections 4.10, 4.12), not a bound chosen in advance, and DNET (Section 4.7) reduces how many NETs a federate has to send. The two architectures therefore move the cost of silence to different places: micro-LF pays it as waiting time at the receiver, bounded by W and independent of the network; centralized coordination pays it in messages and in the latency of the decision, and needs no timing assumption to be correct. Figure 42 sets the two message patterns side by side for one silent tag.

The steps of Figure 42

Choosing W (interpretation). Section 5.3 gives the sufficient condition after + W > E + L + D, which the runtime does not compute. In the program Tardy.ulf of the tutorial edition (Example 16.1) the two federates run on one host, so the clock error E is small and the loopback latency L is far below a millisecond; the sender lag D at count 3 is 100 ms, and the connection has no after. The condition asks for W above roughly 100 ms: 50 ms violates it and 150 ms satisfies it, as the runs showed. Two remarks follow from the mechanism. First, W and after are not interchangeable. An after delay is part of the program: it shifts the tag of every message and changes what the program computes. W is not: while the condition holds it changes only when, in physical time, the receiver commits each tag, and it enters the logical behaviour only through the violations it fails to prevent. Second, D is the term the programmer controls most directly, and a deadline on the sending reaction makes its bound checkable, as in Example 5.1 (Section 5); E depends on the clock synchronization of Section 6, which in micro-LF runs between neighbors along the tree rooted at the grandmaster (Section 5.3).

16.5 — What a hardware implementation would hold

(Interpretation.) Section 9.9 lists what a hardware RTI would have to implement: per-federate records, the min-delay matrix, the EIMT of every node and the grant rules, for the whole federation in one place. The decision of Section 16.3 needs much less, and needs it in every federate rather than in one place: for each incoming federated connection a last_known_tag register and a max_wait constant, the maximum of the constants over the inputs whose register is below the candidate tag, a comparison of the physical clock with t + W against an absolute deadline, and a path by which an arriving message interrupts the wait and restarts the decision. The state grows with the number of the federate’s inputs, not with the size of the federation, and no part of it describes another federate. What it gives up is what Section 16.4 described: absence costs W, the guarantee rests on E, L and D, and a late message is detected and handed to the program rather than excluded. Which of the two is preferable is a property of the application — how often inputs are silent, whether the timing bounds can be established, whether a late value may be handled rather than prevented — and not of the language: both execute the same Lingua Franca semantics, under different assumptions. Figure 43 shows the per-federate datapath next to what the centralized design keeps.

The steps of Figure 43

  1. Per-input state. One register and one constant per incoming federated connection; the comparison with g decides whether the input is still unresolved and so contributes its max_wait.
  2. W and the deadline. A maximum tree over the gated constants yields W; an adder forms g.t + W and a register keeps it as an absolute deadline.
  3. Clock and restart. The synchronized clock, a counter corrected by offset and rate, is compared with the deadline. A message arrival restarts the decision, as notify() does in software. The box on the left recalls what the centralized alternative keeps instead.

How to read Figure 43. The datapath has three stages, one for each part of the decision of Section 16.3.

Stage 1, one copy per input. Each incoming federated connection has a register that holds its last_known_tag, written by the receive path whenever a message arrives, and a constant that holds its max_wait, fixed when the program is compiled. A comparator checks whether the register is below the candidate tag g. If it is, the input is still unresolved and its max_wait is passed on; if it is not, the input is resolved and passes nothing.

Stage 2, the deadline. A maximum over the values passed on gives W, the longest wait that any unresolved input asks for. An adder forms g.t + W, and a register keeps it as an absolute deadline. When every input is resolved, W is zero and the deadline is g.t itself.

Stage 3, the commit. A comparator watches the synchronized clock and signals the commit when the clock reaches the deadline. If a message arrives first, it updates its register and the decision starts again at stage 1, while the deadline register keeps its value, as the software does in Section 16.3.

What the figure shows. All the state is local: one register and one constant for each input of this federate. The centralized design of Section 9.9 instead keeps the min-delay matrix and the grant logic for the whole federation in one place. Because the datapath holds nothing about the other federates, it cannot learn that an input is absent; it can only wait until the deadline, and that wait is the cost of absence described in Section 16.4.

16.6 — Platforms and hardware requirements

What a platform must provide. The runtime is split in two layers (Figure 44). The code the compiler generates for the program and the runtime core — scheduler, event queues, federated coordination, the synchronized clock — are the same C source on every target. Only two small interfaces differ from one platform to another, and porting micro-LF to new hardware means implementing them. A platform implements the Platform interface — get_physical_time in nanoseconds, wait_until and wait_for, wait_until_interruptible, which must return early when notify is called from an interrupt or another thread, and a Mutex with lock and unlock — and, for a federated program, at least one NetworkChannel: open_connection, is_connected, send_blocking, and either a receive callback (an asynchronous channel) or a poll function that the scheduler calls (a polled channel)[49]. Read as hardware requirements, this is a short list: a time source that can be read as a monotonically increasing count, a way to sleep until a time that an interrupt can cut short, a way to make a critical section, and a communication peripheral with a driver. The synchronized clock does not have to be a hardware feature: the runtime keeps it in software, as the hardware count corrected by an offset and a rate (Section 16.2). Nor is a heap needed: every queue and buffer is sized at compile time, by the generator and by the annotations @max_pending_events and @buffer[49].

The steps of Figure 44

  1. Program. The application is ordinary Lingua Franca plus micro-LF annotations; the compiler emits a C project per federate in which every queue and buffer has a size fixed at compile time.
  2. Runtime core. Scheduler, queues, the federated environment, the coordinators and the software-corrected PhysicalClock are the same portable C on every platform; messages are serialized with nanopb.
  3. Two interfaces. A platform supplies five functions and a mutex; a federated program also needs a NetworkChannel, either asynchronous (with a receive callback) or polled.

Why the clock and the channel matter more than the processor. (Interpretation.) The tag decision of Section 16.3 is cheap on any processor; what the hardware decides is how small the timing terms can be. The resolution of the time source is a floor under both E and W: a clock that advances in steps of 1 ms, as on Zephyr at the examined commit, or of one FreeRTOS tick, quantizes the commit instant t + W and the timestamps of the synchronization exchange, so a bound below the step cannot be honoured. The channel sets L and the residual of the synchronization: a TCP connection over a shared network brings variable delay and, as Figure 39 notes, an asymmetry the exchange cannot see; a UART or a dedicated link has fixed latency; and a time-division network-on-chip such as the S4NOC on Patmos (Section 10.2) bounds L by construction. The two FPGA soft cores in Table 12, FlexPRET (Section 10.1) and Patmos, are thus the targets on which the assumptions of decentralized coordination come closest to properties of the hardware, the theme of Section 10; at the examined commit only Patmos has a federated channel for micro-LF, and its documentation page describes a different, statically scheduled flow.

Each executable has about 67 KB of code, 2.4 KB of initialized data and 24.5 to 24.9 KB of zero-initialized data, the last holding every queue, pool and message buffer; the C library is linked dynamically and not counted. These are measurements of this project on a desktop target, not a microcontroller footprint: code size depends on the instruction set and the compiler, and the static data on the sizes the program declares. For microcontrollers, the comparison of the reactor-uc and reactor-c code generators on an RP2040 reports a memory footprint very similar for the two runtimes, the reactor-uc runtime being slightly smaller, without giving figures in the text[50].
